# 正则引擎：现状的缓解措施，与最终替换设计

> **状态**：
> - §1 的**缓解措施已实现**（阶段 1 交付，有回归测试）；
> - §2–§4 的**自动机替换是设计**，尚未实现。
>
> **不要把 §1 当成"问题已解决"。** 审计的原话是：
> 「这是临时缓解，不能当最终方案」。这一页写清楚为什么，以及怎么走到终点。

---

## 0. 为什么要自己写正则，以及代价

拼写代数需要正则（RIME 用 `boost::regex`）。本项目核心零第三方依赖，
于是只有两条路：引入 `regex` crate，或写一个够用的子集。选了后者。

代价在阶段 1 被实测暴露出来——**回溯引擎在病态模式上是指数时间**：

| 模式 | 输入 | 实测 |
| --- | --- | --- |
| `^(a+)+$` | 20 个 `a` + `b` | 约 54 ms |
| 同上 | 24 个 | 约 848 ms |
| 同上 | 28 个 | 3 秒超时（审计的中止线） |

更严重的是**代码注释当时写着「模式是方案作者写死的，输入是一个音节，
不存在指数爆炸的风险面」**——而同一份实现也被 `recognizer` 用，
那里的输入是用户敲的任意长度字符串。注释里的假设与真实调用点不一致，
这就是缺陷本身。

## 1. 已实现的缓解（阶段 1）

三道闸，全部有测试（`crates/stele-engine/tests/regex_and_recognizer.rs`）。

### 1.1 编译期拒绝"重复套重复"

`RegexError::NestedRepeat`：`(a+)+`、`(ab*)*`、`(a?){2,}` 一律编译失败。

**为什么是保守拒绝而不是精确判定**：精确判定"哪个模式会指数回溯"需要分析
字符集重叠与歧义性，而那本身容易判错；判错的方向是**放过**，代价是卡顿。
真实方案的拼写规则里没有任何嵌套量词（只有 `^([a-z]{2}).+$` 这种平铺写法），
所以"一律拒绝"的代价接近零，收益是**可证明**的：没有嵌套重复就没有经典的
指数回溯路径。

### 1.2 运行期步数与深度预算

- `DEFAULT_STEP_BUDGET = 100_000`，每次 `match_node` 进入扣一；
- `MAX_DEPTH = 1024`，**迭代深度也计入**（否则 `a+` 的深度永远停在 0，
  深度上限形同虚设——实测一条 20 万字符输入会直接 SIGABRT）；
- 超限的语义是**不匹配**（不是 panic，也不是继续跑）。

**代价必须说清楚**：超过 1024 个字符的输入不会被量词匹配上。
对 `recognizer` 的前缀模式（`^uU[a-f0-9]+$` 这类）不构成问题——
真实输入是几个到几十个字符。但这是一个**真实的行为边界**，不是"没有限制"。

### 1.3 `leading_literal` 的假阴性修复

旧版本用字符串扫描近似抽取必需前缀，把"某一分支/可选项的首字符"当成
必需前缀，产生**假阴性**：

| 正则 | 输入 | `Regex` 本身 | 旧 `leading` | Recognizer |
| --- | --- | --- | --- | --- |
| `^(a\|b)+$` | `bbb` | 匹配 | `"a"` | 未认领 |
| `^https?://.*$` | `http://x` | 匹配 | `"https"` | 未认领 |
| `^a?b$` | `b` | 匹配 | `"a"` | 未认领 |

现在从**语法树**上取（`Regex::required_prefix`）：跳过开头的 `^`，
连续吃掉字面 `Char` 节点，遇别的节点就停。这**可证明**是全部匹配的公共
必需前缀。优化只能产生假阳性（多做一次完整匹配），不能产生假阴性。

## 2. 为什么缓解措施不够

1. **步数预算会静默吞掉匹配**：一条本来该匹配的输入，如果模式恰好很费，
   就变成"没认领"。用户看到的是"某个前缀偶尔不好使"——正是
   `spec.rs` 里自己写着"最难查的一类 bug"。
2. **深度上限是真的功能边界**：它随输入长度生效，而输入长度由用户决定。
3. **编译期规则只挡住了已知的形态**：`a*a*a*a*b` 这类**平铺但组合爆炸**
   的模式仍然要靠预算兜底（实测里有这条测试）。
4. **正确性论证依赖"真实方案不这么写"**：那是关于**数据**的论断，
   不是关于**引擎**的保证。外部来的 Rime 方案不受我们控制。

## 3. 最终替换：保证多项式时间的匹配器

### 3.1 选择

两条路：

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| **引入经审计的 `regex` crate** | 立即可用、经过大量对抗性测试 | 违反核心零依赖；许可证要进 notices；包体变大 |
| **自写 Thompson NFA / Pike VM** | 保持零依赖、行为完全可控 | 约 300 行，需要仔细的语义对照与 fuzz |

**建议：自写 Pike VM。** 理由：

- 支持的语法很小（见 `regex.rs` 模块文档的表格）；
- Pike VM 在**左端优先 + 贪婪**语义下与回溯引擎等价，而最坏时间是
  **O(长度 × 指令数)**——这是我们要的那个保证；
- 捕获组的语义（`$1`…`$9`）在 Pike VM 里有标准做法（线程各自的
  capture slot 数组）；
- 零依赖是这个项目的既有承诺，不该为了一个 300 行的组件破例
  （要破例也可以，但那是**另一个决定**，需要单独的论证与许可门禁更新）。

### 3.2 构造

```text
Regex ──compile──► Program { insts: Vec<Inst> }
Inst = Char(c) | Any | Class(..) | Split(a, b) | Jump(a)
     | Save(slot) | Start | End | Match
```

- `Concat` → 顺序拼接 + `Jump`
- `Alt` → `Split` 到各分支
- `Repeat{min,max}` → 展开成 `min` 份 + `(max-min)` 份可选（`max=None` 时
  用回边），并在编译期对展开后的**指令数**设上限（例如 100 000），
  超限报 `RegexError::Unsupported`；
- 执行：按优先级排列的线程列表，每次前进一个字符位置；
  **同一 PC 只保留优先级最高的那个线程**（这正是"多项式"的来源）。

### 3.3 与现有 API 的兼容

对外 API 不变：`compile` / `is_full_match` / `find` /
`match_prefix_len` / `replace_all` / `required_prefix`。
语义由现有测试 + 新增的**对照测试**钉住：

- 对全部既有测试模式，回溯结果与 Pike VM 结果必须一致；
- 随机模式 + 随机输入的一致性测试（无依赖的"fuzz"）：
  用一个确定性随机源生成语法树，两种实现分别匹配，结论必须一致。

### 3.4 复杂度

- 编译：O(模式长度)（展开 `{n,m}` 之后是 O(展开后长度)）；
- 匹配：**O(输入长度 × 指令数)**，与模式形状无关——`(a+)+` 也不例外；
- 空间：O(指令数 × 捕获组数)（每个位置一份线程表）。

### 3.5 落地后可以删掉什么

- 步数预算与深度上限（不再需要，但**保留**作为防御性断言）；
- `NestedRepeat` 编译期拒绝（Pike VM 不会指数爆炸；
  但保留它仍然能挡住"用户以为很快、其实是无意义的模式"，需重新评估）。

## 4. 落地顺序与验收

| 步骤 | 内容 | 验收 |
| --- | --- | --- |
| 1 | 加 `Program` 与 NFA 编译器（与回溯引擎并存） | 两种实现在全部既有测试上一致 |
| 2 | 一致性 fuzz（确定性随机模式 × 随机输入） | 无分歧 |
| 3 | 切换默认实现，保留回溯引擎作为参考实现（`#[cfg(test)]`） | 全测试绿 |
| 4 | 删掉回溯引擎与它的缓解措施 | 代码量下降，`NestedRepeat` 处理需重新定夺 |

**在步骤 3 完成之前，§1 的三道闸必须留在原位。** 它们是当前的正确性边界。
