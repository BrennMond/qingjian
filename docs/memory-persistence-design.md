# 用户记忆的持久化设计：状态机、并发、生命周期

> **状态**：§1–§6 **已实现**（阶段 1 交付，有回归测试）；
> §7 的 Android 生命周期是**合同**（前端还没开发，先把边界定下来）；

## 0. 审计的复现（修复前）

```text
flush() -> Err(IsADirectory)
dirty == false
移除障碍后再次 flush() -> Ok(false)
目标文件不存在，内存中的记录未被保存
```

一次写盘失败会**永久关掉之后所有重试的机会**：用户学到的东西一次都存不下，
而且没有任何提示。这是 P0（会静默丢失用户数据）。

另外两条同批发现：

- 两个 `FileMemory` 句柄依次保存，**后写者覆盖先写者**的数据；
- `cap=1` 重开一份含 10 条的文件，**仍然加载 10 条**（上限在恢复路径不成立）。

## 1. 落盘是一台状态机

顺序**不能**调换。任何一步失败都保留 `dirty`。

```text
① 拿文件锁（<path>.lock，跨进程互斥）
② 读盘上的当前文件，逐键**合并**进内存
③ 取快照：编码成字节，记下快照代次 g
④ 写同目录唯一临时文件 → fsync → rename → fsync 目录
⑤ 成功之后才 saved = g
⑥ 放锁（Drop 守卫，异常路径也放）
```

### 为什么是"代次"而不是布尔 `dirty`

落盘要先把快照编码，再做一段可能失败的 I/O。用布尔量时，
"快照之后、清 dirty 之前"发生的并发写入会被一并当成已保存而丢掉。

```rust
struct Inner { entries, predictions, generation: u64, saved: u64 }
impl Inner { fn is_dirty(&self) -> bool { self.generation != self.saved } }
```

- 每次修改 `generation += 1`；
- 落盘成功时 `saved = 快照时的 generation`（**不是**当前 generation）。

推进一步的意义：快照之后新学的词不会因为"某次落盘成功了"被当成已保存。

### 为什么临时文件名不能固定

旧实现用 `<name>.tmp`。两个后果：

1. 两个写者会往**同一个**临时文件里交错写，产出一份谁的内容都不对的产物；
2. 若 `<name>.tmp` 恰好是个目录（用户环境里真的会），`write` 稳定失败，
   而旧实现此时已经清了 dirty，**连重试都没有**。

新实现：`<name>.tmp.<pid>.<counter>`，同目录（保证 `rename` 原子）。

## 2. 并发策略：文件锁 + 版本合并

审计给了三选一：**文件锁、版本比较+合并、单 writer 服务**。
这里选**前两个的组合**，并且明确文档化。

- **锁**：`std::fs::File::lock()`（Rust 1.89 稳定）。
  这解释了一次 MSRV 提升（`1.82 → 1.89`）：备选是引入第三方锁 crate
  （违反"核心零依赖"）或自己写"锁目录 + 陈旧锁清理"（一段容易写错的并发代码）。
  锁文件独立于数据文件：数据文件的 `rename` 会换 inode，
  锁必须挂在**一个稳定的名字**上，否则两个写者各锁各的。
- **合并策略：逐键取更大值**（次数、衰减频次、最后使用时间），而不是相加。

  为什么取更大值：相加会让"同一份数据加载两次"凭空翻倍；
  取更大值是**幂等**的——合并自己刚写的文件不改变任何数字，
  因此单写者场景下合并是恒等变换，多写者场景下它是并集。
- **坏文件不覆盖**：盘上文件解码失败时**中止 flush 并报错**，保留 dirty。
  用户仅有的记录不能被一次失败的读覆盖掉。

### 仍然存在的限制

- 锁是**咨询锁**（advisory）：不遵守约定的进程仍可写坏文件。
- 组合策略是"并集"，**没有因果序**：如果两个实例分别删除了同一条记录，
  并集会让它复活。删除语义要等 `ForgetRequested` 带上完整键（含上下文）
  之后再设计——现在是**已知缺口**，不是"已实现"。
- 合并是 O(文件大小)：`flush` 会重读一次盘。它**不在按键路径上**，
  但前端要避免在热路径里调它（见 §7）。

## 3. 恢复路径必须遵守容量上限

`open_with` 在装载之后、返回之前施加 `cap` / `predict_cap`

**为什么恢复路径最需要它**：前端在**启动时**打开记忆，而那正是内存最敏感
的时刻。旧实现只在"新记录导致超限"时淘汰，于是恢复可以被一份大文件直接顶穿。

## 4. 权限

新建/替换的记忆文件在 Unix 上是 `0600`（所有者读写）。

- 实现方式：临时文件用 `OpenOptionsExt::mode(0o600)` 创建，
  `rename` 之后目标文件继承它的模式。
- **权限不是完整的隐私方案**：父目录权限、系统备份、日志、以及
  "记忆内容本身含上屏文本与时间"都在范围外。见 `docs/privacy-model.md`。
- Android 侧要求 app-private storage（`getFilesDir()`），不是"外面能读的目录"。

## 5. Android 前端生命周期合同（**待前端实现**）

前端还没有开发（审计明确不把"没有手机前端"当当前代码缺陷）。
但**边界现在就要定**，否则"什么时候存、失败了怎么办"会变成前端各写各的。

| 时机 | 动作 | 理由 |
| --- | --- | --- |
| 每次上屏 | **只改内存**，不落盘 | 按键路径零 I/O 是红线（有测试守着） |
| 连续输入空闲 **≥ 30 s** | debounce 落盘 | 避免"打一句存一次"的写放大 |
| `onStop()` / 进程退到后台 | 立即落盘 | 系统可能在后台直接杀进程 |
| `onTrimMemory(TRIM_MEMORY_UI_HIDDEN)` | 落盘 + 释放非必需缓存 | 前台 UI 已不可见 |
| 进程正常退出 | 落盘（最后一道） | **不能只依赖这一条** |
| 落盘失败 | **保留 dirty**，下次时机重试；连续失败要在设置页可见 | "静默不生效"是这个项目反复踩的坑 |

**不做的事**：不在 `onPause()` 同步落盘（会拖慢切换）；
不在按键处理里落盘；不因为落盘失败就降级成"没有记忆"。

## 6. 隐私相关的读写边界

- 用户记忆**默认关闭**：不给 `--userdb` 就没有记忆，行为逐字节可复现。
- 损坏的记忆**不会自动覆盖**（降级得到的实例 `writable == false`）。
- **敏感输入禁学**（阶段 4 的 API）：密码框 / 私密应用 / 明确标记的输入
  不应进入记忆。接口设计见 `docs/privacy-model.md`，实现待阶段 4。
- 导出：`snapshot()` / `prediction_snapshot()` 是"到底学到了什么"的只读出口。
