## 1. 术语表

引擎设计里的每个名词，这里用人话解释一遍。**本文档中任何专业名词首次出现时都会给出解释。**

| 名词 | 解释 |
| --- | --- |
| **struct（结构体）** | 一张登记表。把相关的几栏钉在一起，例如"候选"这张表上有文字、备注、分数、来源几栏。 |
| **enum（枚举）** | 一道单选题。例如"来源"只能是「用户词 / 系统词 / 造句 / 简拼 / 纠错」之一。 |
| **trait（特征）** | 一份岗位说明书。只规定"必须会做哪几件事"，不规定"具体谁来做、怎么做"。 |
| **实现（impl）** | 某个具体类型签下说明书去上岗。例如"拼音翻译器"实现"翻译器"这一 trait。 |
| **`&self` / `&mut self`** | `&self` = 只读；`&mut self` = 要修改自己，且同一时刻只能有一个修改者（Rust 自动保证）。 |
| **`Box<dyn T>`** | 一个"放在别处的盒子"，里面装的东西**种类不限，只要符合 `T` 这份说明书**。 |
| **`Send` / `Sync`** | 线程安全标签。`Send` = 可以搬去别的线程；`Sync` = 可以被多个线程同时读。 |
| **Engine（引擎）** | 加载好的方案 + 词库 + 服务。构造昂贵，**整个进程共享一份**。类比：电话总机。 |
| **Session（会话）** | 一次输入过程的状态。每个客户端（每个窗口 / 每次输入）一份，**很轻，用完即弃**。类比：一通电话。 |
| **Lexicon（词库）** | 本项目的用词，指"**编码序列 → 词条**"的查找器。类比：一本按编码排序的字典。**它不知道"拼音"是什么**（见 §2.4）。 |
| **Code unit（编码单元）** | 构成一个编码的最小单位。**这是通用词**：拼音方案里一个编码单元就是一个音节（`ni`、`hao`、`xian`）；仓颉方案里一个编码单元就是一个字母（代表一个字根）；五笔方案里同理。 |
| **Code（编码）** | 编码单元的序列，是查词典的键。`ni hao` 是编码，`n h`（简拼）也是编码。 |
| **Code alphabet（编码字母表）** | 该方案允许出现的全部编码单元。拼音方案约 400 个音节；仓颉方案 24 个字母。**它是方案的数据，不是引擎的知识。** |
| **Spelling（拼写）** | 用户实际敲出来的表面字符串。同一个编码可以有多种拼写（`ni hao`、`n h`、`ni'hao`）。 |
| **Prism（棱镜 / 切分图）** | 把一段拼写展开成"所有可能的编码切分，以及每种切分的代价"的数据结构。通用，不含任何拼音知识。 |
| **span（范围）** | 一段区间，例如"输入串的第 0 个字节到第 6 个字节"。 |
| **字节偏移** | 字符串里第几个**字节**。一个汉字在 UTF-8 里占 3 个字节，所以字节数 ≠ 字数。 |
| **对数域（log domain）** | 分数用"概率的对数"表示。好处：概率连乘变成连加，不会下溢。**越大越靠前。** |
| **全序（total order）** | 任意两个元素都能比出先后，不存在"分不出先后"的情况。这是**结果可复现**的前提。 |
| **mmap（内存映射）** | 把磁盘文件直接"贴"进内存地址空间，用到哪一页才加载哪一页。词库大但常驻内存小的关键。 |
| **部署 / 编译（deploy）** | 把文本词库（`.dict.yaml`）转换成紧凑二进制（`.table.bin` 等）的过程。发生在使用前，不在按键路径上。 |

> **术语对照**：RIME 源码里管"编码单元"叫 **syllable**，管"编码字母表"叫 **syllabary**——这是历史遗留的用词（因为 RIME 诞生于拼音方案），**即使仓颉方案的"音节"其实只是单个字母**。本项目对外的通用词一律用 **code unit / code alphabet**，仅在明确讨论拼音方案时才使用"音节"一词。读 RIME 源码时请记住这个对应关系。

## 2. 分层：Engine 与 Session 🔴

### 2.1 为什么必须分两层

引擎里有两类性质完全相反的东西：

| | 共享的 | 私有的 |
| --- | --- | --- |
| 例子 | 词库、方案配置、记忆服务 | 正在敲的这串字母、当前候选、光标位置 |
| 构造代价 | 昂贵（加载词库） | 廉价（几个 String） |
| 数量 | 进程内一份 | 每个客户端一份 |
| 可变性 | 只读 | 可变 |

把它们塞进同一个 `&mut` 对象，会导致**无法同时开两个输入会话**，也无法安全地多线程共享词库。

### 2.2 接口

```rust
/// 引擎：**方案目录 + 共享服务**。构造昂贵，进程内共享一份。
///
/// `Send + Sync` 是对编译器的承诺："这个东西可以安全地被多个线程共享。"
///
/// **注意（审计修正）**：早先的版本让 `Engine` 等同于"一个已加载的方案"，
/// 同时又给了它 `schema_id()`——这与 D29（会话内可切换方案）**直接冲突**。
/// 现在明确分两级：
///
/// ```text
/// Engine（应用级，一份）
///   ├── SchemaCatalog：已装载方案的集合（惰性装载 + LRU 淘汰，D29）
///   ├── 共享服务：MemoryStore / Clock / …
///   └── create_session() → Session（每个客户端一份）
/// Session（客户端级）
///   └── 当前方案句柄 + 输入状态
/// ```
pub trait Engine: Send + Sync {
    /// 为一个客户端创建独立会话。多次调用互不影响。
    ///
    /// 返回 `Box<dyn Session + Send>` 而非 `Box<dyn Session>`：
    /// **不加 `Send` 的话，会话连"搬到另一个线程"都不允许**，
    /// 而 Windows TSF 组件（跑在别人的进程里）与前端的工作线程都需要搬。
    fn create_session(&self) -> Box<dyn Session + Send>;

    /// 方案目录：列出 / 取用 / 淘汰（D29）。
    fn schemas(&self) -> &dyn SchemaCatalog;
}

/// 会话：一个客户端的私有状态。
///
/// 注意这里**故意不写 `Send + Sync`**：Rust 会因此在编译期保证
/// "同一个会话不可能被两个线程同时修改"——这是 RIME 靠口头约定
/// （"一个 session 一个线程"）才能换来的东西，我们免费拿到。
pub trait Session {
    /// 送入一个按键，推进输入状态机。
    fn process_key(&mut self, key: Key) -> Outcome;

    /// 当前输入串与切分结果（只读）。
    fn composition(&self) -> &Composition;

    /// 当前候选列表（已排序）。
    fn candidates(&self) -> &[Candidate];

    /// 选中第 index 个候选。
    ///
    /// `index` 指向 **`candidates()` 返回的那个"已渲染列表"**的位置（两条通道统一编号）；
    /// `source` 区分键盘盲选与明确的点选——**预测候选默认只允许后者**（见 §4.3.3）。
    fn select(&mut self, index: usize, source: SelectionSource) -> Outcome;

    /// 显式上屏当前高亮候选（空格 / 回车）。
    fn commit(&mut self) -> Option<Commit>;

    /// 放弃当前输入。
    fn reset(&mut self);

    /// 按**名字**读取 / 设置开关。
    ///
    /// 引擎不预设任何开关名（D20）——名字全部来自方案声明，
    /// 因此这里的 `name` 是纯粹的字符串，引擎只当它是键。
    fn option(&self, name: &str) -> bool;
    fn set_option(&mut self, name: &str, on: bool);

    /// 切换方案（D29）。**失败时必须保持原方案可用**（§5.6）。
    fn switch_schema(&mut self, schema_id: &str) -> Result<(), SchemaError>;

    /// 引擎侧异步发生的事件（学习通知等）。前端可以忽略。
    ///
    /// **用出参而不是返回 `Vec`**：这个方法在每次按键后都会被调用，
    /// 返回 `Vec` 意味着每次按键都分配（哪怕为空）。出参让调用方复用缓冲区。
    fn drain_events(&mut self, out: &mut Vec<Event>);

    /// **时钟推进（G13 的预留）**：当前时间到了 `now_ms`（由注入的 `Clock` 提供）。
    ///
    /// 目前**没有任何组件需要它**——`process_key` 是唯一入口。
    /// 但并击输入（RIME 的 `chord_composer`）、长按、以及"单键按下超过 N 毫秒
    /// 就当作空格"这类判定**必须**有它。
    ///
    /// **现在就留这个方法**，因为事后往 `Session` 上加方法虽然是加法，
    /// 但**所有前端都要重新实现一遍事件循环**（它们得开始定时唤醒引擎）。
    /// 前端可以永远不调用它——只要默认实现是空操作。
    fn tick(&mut self, _now_ms: u64) {}
}
```

### 2.3 会话的生命周期

- 创建：`engine.create_session()`
- 使用：前端持有它，每次按键调用 `process_key`
- 销毁：直接丢弃（Rust 自动回收）

**不需要** RIME 的"5 分钟空闲回收"机制——那是 C++ 手动管理句柄的产物。但**资源回收必须显式**：会话不持有词库，只持有对引擎的引用。

### 2.4 通用性边界：引擎里没有"拼音" 🔴

> **这是本项目最重要的一条架构不变式。** 它决定了引擎能不能支持拼音以外的输入法，也决定了"方案"是否真的可以自由设定。

#### 2.4.1 分界线

| 属于**引擎**（通用机制） | 属于**方案**（数据，可自由设定） |
| --- | --- |
| 编码单元、编码、拼写这些**概念** | 具体有哪些编码单元（拼音的 400 个音节？仓颉的 24 个字母？） |
| 拼写代数的**运算种类**（`xform` / `derive` / `abbrev` / `erase` / `fuzz`） | **用哪几条规则、规则的内容**（模糊音开不开、简拼取首字母还是前两字母） |
| 在切分图上求最短路的**算法** | 每条边的**代价数值**（简拼罚多少、补全罚多少） |
| "编码序列 → 词条"的**查找** | 词典内容与词条权重 |
| 处理器 / 切分器 / 翻译器 / 滤镜的**流水线骨架** | 用哪些零件、按什么顺序（**顺序本身也是数据**） |

#### 2.4.2 用反例验证

如果分界线画对了，那么下面这些完全不同的输入法应当**共用同一套引擎代码，只换数据**：

| 输入法 | 编码单元是什么 | 需要拼写代数吗 | 需要切分图吗 |
| --- | --- | --- | --- |
| 全拼 | 一个音节（`ni`） | 需要（简拼、模糊音） | 需要（`xian` 有歧义） |
| 双拼 | 一个音节（但用 2 个键敲） | 需要（2 键拼写 → 音节） | 需要 |
| 注音 | 声母 / 韵母 / 介音 | 需要 | 需要 |
| 仓颉 | **一个字母**（代表一个字根） | **不需要** | **不需要**（每个键就是一个编码单元） |
| 五笔 | **一个字母** | **不需要** | **不需要** |
| 英文（`melt_eng`） | 一个字母 | 不需要 | 不需要 |

**仓颉 / 五笔这一行是关键的检验**：它们没有"音节"这个概念，也不需要切分图，只需要"编码 → 字"的精确查表。如果引擎强迫所有方案都走"音节 + 棱镜 + 动态规划"这条路，那它就是把拼音的标准强加给了全世界——**这正是我上一版文档犯的错。**

#### 2.4.3 因此引擎提供**两族**翻译器，由方案选

| 翻译器族 | 做什么 | 谁用 |
| --- | --- | --- |
| **精确编码翻译器**（对应 RIME 的 `table_translator`） | 把输入串当作完整编码，直接查表出候选 | 仓颉、五笔、英文输入、自定义短语、拆字反查 |
| **拼写图翻译器**（对应 RIME 的 `script_translator`） | 先把拼写展开成切分图，在图上求最短路 + 组句 | 全拼、双拼、注音 |

**方案在配置里选哪一族**，引擎不预设。rime-ice 一个方案里同时用了这两族：主拼音走 `script_translator`（拼写图那族），而英文、自定义短语、拆字反查走 `table_translator`（精确编码那族）——这恰好证明它们是可以共存的通用零件。

#### 2.4.4 简拼到底住在哪里（我上一版写错了）

我上一版写"简拼进 `Segmentor`"，这句话**方向对但不精确**，容易读成"引擎里有一段叫简拼的拼音代码"。精确的说法是：

```
① 规则声明        →  方案的 YAML 数据        `abbrev/^([a-z]).+$/$1/`
② 规则编译        →  通用编译器（引擎内）      把规则展开成棱镜里的边
③ 代价数值        →  方案的数据              每条缩写边罚多少分
④ 运行时最短路    →  通用切分器（引擎内）      在图上跑动态规划
```

**引擎代码里没有"简拼"这个概念**，它只知道"这条拼写边有一个代价"。引擎也不知道"模糊音"是什么，只知道 `derive` 运算产生了另一条边。**拼音知识 100% 住在方案数据里。**

#### 2.4.5 如何守住这条线（可执行的检查）

- **命名检查**：引擎的类型名、函数名、注释里**不允许出现**"拼音 / 音节 / 声母 / 韵母 / 简拼 / 模糊音"等词。只允许"编码 / 拼写 / 编码单元 / 字母表"。
  - 例外：文档里举例时可以说"拼音方案下一个编码单元就是一个音节"。
- **依赖检查**：`stele-core` 与 `stele-engine` **不得**包含任何内置词表、音节表或拼音规则文件。它们全部来自方案。
- **测试检查**：P2 之后必须有一组测试，用**同一个引擎 + 一份仓颉方案**跑通"编码 → 字"。**如果这个测试做不出来，说明通用性边界没守住。**
  - 这是对 §2.4.2 那张表的机械化验证，比任何文档声明都可靠。

### 2.5 内核与方案：完整的分界表，以及"我要加个功能该放哪" 🔴

> §2.4 讲的是"引擎里不能有拼音"。这一节把它扩展到**全部**能力，并回答一个更实际的问题：**我想加个东西，该写进内核还是写成方案数据？**

#### 2.5.1 内核提供"机制"，方案提供"个性"

| | 内核（`stele-core` / `stele-engine`） | 方案（数据，随方案包分发） |
| --- | --- | --- |
| **概念** | 编码 / 拼写 / 编码单元 / 编码字母表 / 候选 / 通道 / 段 | 具体有哪些编码单元、候选怎么显示 |
| **扩展点分类** | 处理器 / 切分器 / 翻译器 / 滤镜 / 格式化器 | 用哪些、按什么顺序 |
| **算法** | 最短路、组句、去重、排序、限流 | 每条边的代价、每个零件的参数 |
| **服务接口** | `Lexicon` / `Ranker` / `MemoryStore` / `Clock` 的定义 | 用哪个实现、挂几个 |
| **开关** | 按名字读写的机制 | **所有开关的名字与含义** |
| **拼写改写运算** | `xform` / `derive` / `abbrev` / `erase` / `fuzz` 的语义 | **用哪几条规则、内容是什么** |
| **词库** | 查找接口 | **词条与权重** |
| **默认方案** | ❌ 内核里没有 | ✅ 见 D24：雾凇行为对标的**自有**方案，作为独立资产分发 |

**内核的边界是诚实的**：增加一个新的**扩展点类别**（第五类零件）、或一个新的**服务接口**、或一种新的**改写运算法**，都必须改内核。这和 RIME 一样（写新翻译器要写 C++）。**没人能"只靠配置"凭空造出一种全新机制**——这一点必须说清楚，否则"一切皆可配置"就是空话。

#### 2.5.1b 「这是零件，还是普通函数库？」——一个可机械执行的判据

DSH 的这个判据很干净，值得原样借用（`reference/dsh-plugin-architecture-lessons.md`）：

> **没有上下文、没有状态、不发事件 ⇒ 它是库，不是零件。**

DSH 用它把约 52 个包划成"库"（如纯函数、编解码器），不许它们变成插件；这也解释了为什么它的 `core/scope` 被标注为 "library, no key"。

**对我们的用处**：**不要把纯函数塞进方案 trait。** 具体地：

| 东西 | 是零件吗 | 为什么 |
| --- | --- | --- |
| 拼写代数的求值器 | ❌ **库** | 输入字符串 → 输出字符串，无状态、无上下文 |
| `.dict.yaml` 解析器（`stele-dict`） | ❌ **库** | 纯解析 |
| 排序 / 去重函数 | ❌ **库** | 纯函数 |
| 音节图最短路 | ❌ **库** | 纯算法（喂进去一个图，吐出一个路径） |
| 拼音翻译器 | ✅ **零件** | 持有词库引用、参与流水线、产出候选 |
| 记忆重排器 | ✅ **零件** | 持有存储、读上下文 |
| 简繁滤镜 | ✅ **零件** | 持有转换表，参与流水线 |

**判据的价值**：它防止我们把 `stele-core` 变成一个"什么都往里塞"的杂物间。**库可以零依赖、可以纯 `cargo test`、不需要注册表、不需要生命周期**——把纯算法留在库里，它们才可测、可复用、可裁剪。

#### 2.5.2 "我要加个功能，该放哪"（决策地图）

这张表的形态直接借鉴 DSH 的 "Where new behavior goes"（`dshsrc/docs/architecture.md`）——**它把"一切皆插件"从口号变成了一张可查的表**，这是它比我上轮说的"三个问题"更实用的地方。

| 我想…… | 该做什么 | 需要写 Rust 吗 |
| --- | --- | --- |
| 换一套按键 → 输入的逻辑（如中英切换） | 写一个处理器，或改方案的处理器列表 | 可能要 |
| 支持一种新的切分方式 | 写一个切分器，挂进方案 | 是 |
| 支持一种新的"输入 → 候选"方式 | 写一个翻译器，挂进方案 | 是 |
| 改候选的显示/过滤（置顶、简繁、去重） | 写一个滤镜，挂进方案 | 可能要 |
| 改预编辑串/备注的显示格式 | 写格式化器的配置（通常不用写代码） | 否 |
| **换一个输入法**（全拼→双拼→仓颉） | **写一份新方案 YAML** | **否** |
| 加一个开关（如 emoji、简繁） | 在方案里声明 | 否 |
| 改某条拼音规则（模糊音、简拼） | 改方案的拼写代数 | 否 |
| 加词、调词频 | 改词库数据 | 否 |
| 换一整套词库 | 在方案里指定 | 否 |
| 加按键绑定 / 翻页键 | 改方案的按键配置 | 否 |
| 改标点表、符号表 | 改方案数据 | 否 |
| 加"下一词预测" | 装配一个预测翻译器 + 预测数据 | 可能要 |
| 改候选排序偏好（个人习惯） | 装配一个重排器 | 可能要 |
| 换存储后端 | 实现 `MemoryStore` | 是 |
| 让某个功能不占内存 | 不装配它 | 否 |

**判定规则（一句话）**：**如果它是"数据能描述的选择"，就属于方案；如果它需要"新的控制流"，就属于内核。**

#### 2.5.3 用户能改到什么程度

方案的**分层组合**（借鉴 DSH 的 profile / bundle / patch 三层模型，见 §6.2）：

1. **基准默认**：方案自带的完整配置。
2. **方案包的补丁**：方案包内部按层叠加。
3. **用户补丁**：用户只写**差异**，不改原文件。
4. **命令行覆盖**：临时试一把。

且必须提供 **`stele --dump-config`**——打印**合并后**的完整方案，**打印出来的每一行都能被用户补丁覆盖**。这样"可配置性"不是靠文档描述，而是**可发现、可验证**的。

### 3.1 `Key`：按键 🟡

```rust
/// 修饰键的位集合。零依赖，手写而非用 bitflags crate（见 PLAN D9）。
#[derive(Clone, Copy, PartialEq, Eq, Default)]
pub struct Modifiers(u8);

impl Modifiers {
    pub const NONE:  Self = Self(0);
    pub const SHIFT: Self = Self(1 << 0);
    pub const CTRL:  Self = Self(1 << 1);
    pub const ALT:   Self = Self(1 << 2);
    pub const SUPER: Self = Self(1 << 3);  // Windows 键 / Command 键
    pub const CAPS:  Self = Self(1 << 4);
}

/// 按键的"是什么"。
#[derive(Clone, Copy, PartialEq, Eq, Debug)]
pub enum KeyCode {
    /// 可打印字符。已做归一化：Shift+a 在这里就是 'A'。
    Char(char),
    /// 具名功能键。
    Named(NamedKey),
}

#[derive(Clone, Copy, PartialEq, Eq, Debug)]
pub enum NamedKey {
    Backspace, Delete, Enter, Escape, Space, Tab,
    Left, Right, Up, Down, Home, End, PageUp, PageDown,
    Digit(u8),   // 顶部数字键 0–9，用于选词
}

#[derive(Clone, Copy, PartialEq, Eq, Debug)]
pub struct Key {
    pub code: KeyCode,
    pub mods: Modifiers,
    /// 是否是"松开"事件。绝大多数输入法逻辑只处理按下。
    pub release: bool,
}
```

**为什么不直接用 RIME 的 X11 keysym 编码？** keysym 是从 Unix 借来的历史产物，Windows 与 Android 前端都要为此写一大坨映射表。我们**内部用自己的类型**，只在 FFI 边界提供 keysym 兼容层。

**归一化规则**：前端负责把平台按键转换成 `Key`。`Shift` + 字母的处理由前端的 `mods` 表达，`KeyCode::Char` 里存归一化后的字符。

### 3.3 `Candidate`：候选 🔴（分数语义）

```rust
/// 候选分数：**定点整数**的"对数分"。
///
/// 单位是**毫对数**（milli-log）：1 个单位 = 0.001 的 ln 值。
/// 因此 `Score(16_118)` ≈ `ln(1e7)` ≈ 16.118，约等于权重一千万。
///
/// # 为什么不用 f64（D13）
///
/// 我们的铁律第 2 条要求"同一输入永远逐字节相同"。但**浮点加法不满足结合律**，
/// 以下情况都会破坏它：并行归约、遍历 `HashMap` 累加、以及**不同平台 / 不同 libm
/// 的 `ln`/`exp` 可能差 1 ULP**——而我们同时要跑 Windows x86-64 与 Android ARM。
///
/// 定点整数的加法与比较是**精确**的，跨平台逐位一致。
/// **关键洞察：`ln` 只在编译期需要算**——把词频转成分数时用 f64 算完、取整、存表，
/// **运行时只做整数加法和比较**，永远不需要 `ln`。
///
/// # 附带的三个好处
/// - **内存**：4 字节 vs f64 的 8 字节（直接服务 §0.2 红线）
/// - **速度**：整数加法/比较更快，且没有 NaN 分支
/// - **铁律可被算术保证**：整数天然全序，**NaN 问题从根上消失**（见 §5.3.1）
#[derive(Clone, Copy, PartialEq, Eq, PartialOrd, Ord, Debug, Hash, Default)]
pub struct Score(i32);

impl Score {
    pub const ZERO: Score = Score(0);

    /// 下界，替代 `ln(0) = -∞`。约 `ln(1e-9)` ≈ -20.72。
    /// 所有权重为 0、概率为 0 的情形都钳到这里，**永不产生 -∞ 或 NaN**。
    pub const FLOOR: Score = Score(-20_723);

    /// 由权重（正数）构造分数。
    ///
    /// **只允许在编译期 / 加载期调用**，因为它内部用了浮点 `ln`。
    /// 运行期的按键路径上**禁止**调用本函数（§5.7）。
    pub fn from_weight(w: f64) -> Score {
        if !(w > 0.0) { return Score::FLOOR; }   // 同时挡住 NaN 与 0
        Score((w.ln() * 1000.0).round().clamp(-20_723.0, 21_474.0) as i32)
    }

    /// 相加：**饱和**而不是溢出。
    /// 这是"AI 不许压过精确匹配"能被算术保证的一半（另一半见 §5.3.1）。
    pub fn saturating_add(self, rhs: Score) -> Score {
        Score(self.0.saturating_add(rhs.0))
    }
}
```

**定点数的具体约定**（必须在 `stele-core` 里写死并有测试）：

| 项 | 值 |
| --- | --- |
| 底层类型 | `i32` |
| 精度 | 1 单位 = 0.001 ln（毫对数） |
| 表示范围 | 约 `ln(1e-9)` 到 `ln(2e9)`，覆盖一切现实权重 |
| 下界 | `Score::FLOOR`（替代 `-∞`） |
| 运算 | 只有 `saturating_add` 与比较；**禁止乘法**（乘权重在加载期就做完了） |
| 转换 | `f64 → Score` 只允许在加载期；**禁止反向转换**（调试工具除外） |

> **与 PLAN §6 里那条待决问题的关系**：这条现已确定为 D13 的组成部分——**对数域 + 定点整数**。理由是它同时服务"可复现""内存""铁律可强制"三件事。

```rust
/// 这条编码**是怎么被拼出来的**——位集，**可以叠加**（G9）。
///
/// 来自 RIME 的拼写运算：`fuzz` 给派生拼写附加「模糊」属性，
/// `abbrev` 附加「缩略」属性，**两者可以同时成立**。
/// 用单选题（旧版的 `Source`）表达不了，属有损建模。
#[derive(Clone, Copy, PartialEq, Eq, Debug, Default)]
pub struct SpellingAttr(u8);

impl SpellingAttr {
    pub const NORMAL:     Self = Self(0);
    pub const FUZZY:      Self = Self(1 << 0);  // 模糊音
    pub const ABBREV:     Self = Self(1 << 1);  // 简拼
    pub const COMPLETION: Self = Self(1 << 2);  // 补全
    pub const CORRECTION: Self = Self(1 << 3);  // 纠错

    /// 是否经过了任何"变形"——即这条编码不是规范拼写。
    /// 用于 UI 标记（G12）与学习（G10）。
    pub fn is_derived(self) -> bool { self.0 != 0 }
}

/// 候选**从哪来**——单值。
#[derive(Clone, Copy, PartialEq, Eq, Debug, PartialOrd, Ord)]
pub enum Origin {
    // ── 不是猜的（NotGuessed）──
    /// 用户词库里的词（用户打过并确认过）。
    UserWord,
    /// 词库精确匹配。
    SystemWord,
    /// 原样上屏（英文、标点、数字）。输入本身就是答案，不是猜测。
    Literal,
    // ── 猜出来的（Guessed）──
    /// 造句（动态规划拼出来的组合）。
    Sentence,
}

/// 这个候选是不是"输入本身就是答案"，而不是引擎猜的。
///
/// **判据由两个轴共同决定**：来源不是猜测，**且**编码没有被变形。
/// 一条模糊音派生出来的词，即使词库里真有这个词，用户看到的也是"猜的"。
///
/// **全项目只有这一处定义**——排序、断言、重排守卫都复用它。
pub fn is_exact(origin: Origin, attr: SpellingAttr) -> bool {
    matches!(origin, Origin::UserWord | Origin::SystemWord | Origin::Literal)
        && !attr.is_derived()
}
```

> **为什么拆成两个轴（G9 的完整理由）**：旧版把"来源"和"编码怎么来的"挤进一个 `Source` 枚举，于是
> - 一条**同时**由模糊音和简拼派生的编码**无法表达**（只能任选其一，选哪个都是错的）；
> - `Sentence` 与 `Abbrev` 属于两个不同的轴却被并列（造句是"来源"，简拼是"编码形态"）；
> - G12 要求的 **UI 猜测标记**没有数据来源——`Sentence` 该标，但"词库里的词经由模糊音命中"也该标。
>
> 拆开之后：**`Origin` 管"从哪来"，`SpellingAttr` 管"怎么拼出来的"**，`is_exact` 是两者的合取。

> **注意 `Origin` 的声明顺序**：`#[derive(PartialOrd, Ord)]` 使这个顺序**就是平局时的优先级**（靠前 = 优先）。因此**调整枚举顺序等于调整排序行为**。
>
> **两个必须同时满足的条件**（这是设计约束，不是巧合）：
> 1. 所有 `is_exact(..) == true` 的变体必须排在所有 `false` 的前面——否则平局规则会与铁律冲突（§5.3 的断言会失败）。
> 2. `Literal` 之所以排在 `Sentence` 之前，是因为它是"输入原样"，不是猜测；但它的**实际排序位置主要由 `score` 决定**（rime-ice 给英文的 `initial_quality` 低于拼音，所以中文通常仍在前）——`Origin` 只在分数持平时起作用。

```rust
/// 候选属于哪条通道（D23）。
///
/// 这是让"精确优先"与"下一词预测"同时成立的关键：**两者的规则完全不同**，
/// 混在一个列表里用一套规则管，必然二选一地牺牲掉一方。
#[derive(Clone, Copy, PartialEq, Eq, Debug)]
pub enum Lane {
    /// 对应当前输入的候选：`nihao` → 你好。
    /// 严格规则：全序、精确优先、参与"第 N 个就是我要的"盲选、计入学习。
    Input,
    /// 对"你接下来可能想打的词"的猜测：微信 → 朋友圈。
    /// 宽松规则：可混排、数量受限、**不参与盲选**、学习单独计、可一键关闭。
    Predict,
}

#[derive(Clone, Debug)]
pub struct Candidate {
    /// 上屏的文本。
    pub text: String,
    /// 候选窗右侧的备注（拼音、来源说明等）。
    pub comment: Option<String>,
    /// **对数域**分数（定点整数，见上）：越大越靠前。
    /// 天然全序，**不存在 NaN**，因此排序永远可复现（§5.4）。
    pub score: Score,
    /// 候选从哪来——决定平局优先级与学习行为。
    pub origin: Origin,
    /// 这条编码是怎么拼出来的——位集，**可叠加**（G9）。
    /// 同时用于 UI 的"猜测"标记（G12）与学习主键的规范化（G10）。
    pub attr: SpellingAttr,
    /// 覆盖输入串的哪一段。
    ///
    /// **`Lane::Predict` 的候选没有对应的输入**，此时必须填
    /// `Span { start: caret, end: caret }`（caret 处的空区间），
    /// 不得复用别的候选的 span，也不得填 0..0 以外的值——否则
    /// "按 span 切分/上屏"的逻辑会误伤输入串。
    pub span: Span,
    /// 所属通道。
    pub lane: Lane,
}
```

**三条不变式（写进代码断言，见 §5.3）**

1. `score` 在**对数域**：所有概率型贡献都是 `ln(p)`，加法即"乘以概率"。
   - 为什么必须现在定：`score` 的语义会渗透 translator、filter、ranker、记忆层四处。P5 接向量重排时才发现"基础分是线性、AI 分是对数"，就得全部返工。
   - **并且必须是定点整数**（D13）：`ln` 只在加载期算，运行时只做整数加/比较。理由见上面的 `Score` 定义。
2. `score` **类型上不可能**是 NaN——`Score` 是 `i32`，NaN 根本不存在。这是选择定点而非浮点最直接的收益之一。
3. `text` 非空。

**反面参考**：RIME 把分数拆成 `quality`、`credibility`、`quality_len` 等好几个字段，并在不同位置用**线性值**相加：

```cpp
quality = exp(entry->weight) + initial_quality + quality_len / full_code_length
```

而 `exp(weight)` 就是**原始权重计数**（雾凇里 `阿爸 → 6170`，冷门词 → `1`）。所以这个式子的实际含义是"**计数 + 1.2**"——于是 `initial_quality: 1.2` 对高频词**毫无影响**（6170→6171.2），对冷门词**翻倍**（1→2.2）。

**这不是调参困难，是量纲错误**：一个加性常数无法表达"把某类翻译器的候选整体乘一个系数"。在对数域，同一个配置项变成 `ln(w) + ln(1.2) = ln(w × 1.2)`——**乘性偏置，全分布一致**。

我们统一成一个对数域定点标量：**贡献可加、来源可查、量纲正确**。

### 3.4 `Commit` / `Trigger` / `Outcome` 🔴

```rust
/// 上屏的触发方式。
#[derive(Clone, Copy, PartialEq, Eq, Debug)]
pub enum Trigger {
    Space,        // 空格确认
    Enter,        // 回车确认
    Punctuation,  // 标点自动上屏
    AutoCommit,   // 引擎自动上屏（如候选唯一）
    Explicit,     // 显式选词
}

/// 一次上屏的完整记录。
///
/// `input` 与 `source` 是 P4a（用户记忆）能否实现的前提：
/// 学习需要的三元组是 **(原始输入, 上屏文本, 来源)**。
/// v1 的 `commit() -> Option<String>` 丢掉了其中两项。
#[derive(Clone, Debug)]
pub struct Commit {
    pub text: String,
    /// 触发它的原始输入。
    ///
    /// **`Lane::Predict` 的候选上屏时这里是空字符串**（预测没有对应的当前输入），
    /// 学习时必须改用 `context` 作为键（见下）。这是 D23 引入的必然结果：
    /// "微信 → 朋友圈"这条记录的主键是「上一个词」，不是"输入串"。
    pub input: String,
    /// 上屏时的上下文（最近已上屏的词，最新的在末尾）。
    /// P4a 对 `Lane::Input` 的候选只用到 `input`；对 `Lane::Predict` 只用到它。
    pub context: Vec<String>,
    pub origin: Origin,
    /// 学习时用它判断这条编码是怎么来的；**主键是 [`Commit::key`]**（D42）。
    pub attr: SpellingAttr,
    pub lane: Lane,
    pub trigger: Trigger,
}

/// `process_key` / `select` 的返回值。
pub enum Outcome {
    /// 这个键我不处理，请前端还给操作系统。
    Rejected,
    /// 已处理，前端应重新读取状态并重绘。
    Consumed,
    /// 已处理并且上屏了。**上屏信息是返回值带出来的，前端不可能漏读。**
    Committed(Commit),
}

/// 引擎侧异步事件。前端可忽略。
pub enum Event {
    /// 记录一次学习（P4a 使用）。
    Learned { input: String, text: String, origin: Origin, lane: Lane },
    /// 开关被引擎改动（例如自动切换到英文模式）。
    OptionChanged { name: String, on: bool },
}
```

**为什么不用 RIME 的写法（`bool` + "读取即清空"的 `get_commit`）**

RIME 的 API 是"`process_key` 返回布尔 + 单独调用 `get_commit` 取上屏文本，且读取后即清空"。这有两个真实危害：

1. **漏读一次 = 文字永久丢失**（前端 bug 的经典来源）。
2. **信息丢失**：布尔值不说"这一下上屏了什么"，前端只能再问一次。

我们两端的代码都是自己写的，**没有理由继承这个设计**。

**内部**（processor 之间）仍保留三态，因为语义确实不同：

```rust
pub enum ProcessResult {
    /// 我不管，请走系统默认处理（例如 Ctrl+C）。
    Rejected,
    /// 我不管，但后面的处理器可能管（例如未识别的按键）。
    Noop,
    /// 我处理了。
    Accepted,
}
```

### 3.5 切分：`Segment` / `Segmentation` / `Composition` 🟡

```rust
/// 一段输入的状态。
#[derive(Clone, Copy, PartialEq, Eq, Debug)]
pub enum SegmentStatus {
    /// 还没切分。
    Void,
    /// 引擎给了候选，用户正在选。
    Guess,
    /// 用户选了某个候选，但还没上屏。
    Selected,
    /// 已定死，不再重算。
    Confirmed,
}

/// 切分出来的一段。
#[derive(Clone, Debug)]
pub struct Segment {
    pub span: Span,
    pub status: SegmentStatus,
    /// 标签，例如 "abc"（拼音）、"punct"（标点）、"radical_lookup"（拆字）。
    pub tags: Vec<Tag>,
    pub candidates: Vec<Candidate>,
    pub selected: Option<usize>,
}

/// 标签。用 `&'static str` 而非堆分配的 String：标签来自封闭的已知集合，
/// 方案里自定义的标签在加载期被 interning 成静态字符串。
pub type Tag = &'static str;

#[derive(Clone, Debug, Default)]
pub struct Segmentation { pub segments: Vec<Segment> }

/// 一次输入过程中，输入串的完整状态。
#[derive(Clone, Debug, Default)]
pub struct Composition {
    /// 原始输入，例如 "nihao"。
    pub input: String,
    /// 光标位置（字节偏移）。
    pub caret: usize,
    /// 显示用的预编辑串。拼音方案下可能带音节分隔（例如 "ni'hao"），
    /// 分隔符由方案数据决定；引擎只负责按方案给的格式串拼接。
    pub preedit: String,
    pub segments: Segmentation,
}
```

**"数据模型全要，行为先做一半"**

v1 → P1 阶段：所有 segment 都是 `Guess` + **每次按键从头重算**。
后续阶段：实现 `Confirmed` 的"已定段不再重算"行为（RIME 的 `Forward()` / `Trim()` / `Reopen()`）。

**为什么这样分**：数据结构现在定完整是**便宜的**（struct 多几个字段）；而增量重算的**行为**是 RIME 里最容易出错的部分。用一个几百条的词库时，从头重算只要几十微秒，完全不值得现在做。**将来补行为时不需要改任何类型签名。**

**两个 `candidates` 的关系（易混，明确写下）**

| 位置 | 是什么 | 谁用 |
| --- | --- | --- |
| `Segment::candidates` | 该段**未经合并**的候选（某个翻译器/滤镜作用后的结果） | 引擎内部；调试与测试 |
| `Session::candidates()` | 所有段**合并、跨通道排好序**的最终列表 | **前端只读这个**（§4.3.2） |

**前端永远不要直接读 `Segment::candidates`**——它没有跨段合并、没有跨通道排序、也没有经过最终滤镜。

### 3.6 `Options`：开关 🟢

```rust
/// 一个开关。
#[derive(Clone, Debug)]
pub struct Switch {
    pub name: String,
    /// 显示用的状态名（与方案里的 `states` 对应）。
    pub states: Option<[String; 2]>,
    pub on: bool,
}

/// 会话的开关集合。
///
/// **全部由方案声明，引擎不预设任何输入法专属开关**（D20）。
/// 内部用 `BTreeMap` 而非 `HashMap`：顺序会影响输出的地方一律用有序容器（§5.4）。
#[derive(Clone, Debug, Default)]
pub struct Options {
    switches: std::collections::BTreeMap<String, Switch>,
    /// 引擎自身组件真正需要的少数几个开关的名字，在加载期由方案校验存在性。
    /// 引擎只按**名字**取用，不认识它们的含义。
    required: Vec<&'static str>,
}
```

**⚠️ 这里修正了 v2 初稿的一个 D20 违规**：初稿把 `ascii_mode` / `emoji` / `traditionalization` / `full_shape` / `ascii_punct` 写成了 `stele-core` 里的**结构体字段**。其中 `emoji` 和 `traditionalization` 是 **rime-ice 方案专有的**（换个方案就没有这两个概念），把它们写进核心，等于在引擎里内置了输入法专属知识——**直接违反 D20**。

正确的做法：

- 开关**全部**是方案声明的数据（名字 + 两个状态名 + 默认值）。
- 引擎的组件（例如处理中英切换的处理器）**按名字**申请它需要的开关，加载期校验该开关在方案里存在；名字对不上就报错，而不是静默失效。
- 于是"全角 / 半角""简繁""emoji"在引擎眼里**都是同一种东西**：一个有名字的布尔量。

**与 RIME 的差异**：RIME 的 `RimeStatus` 把 `is_ascii_mode` / `is_full_shape` / `is_simplified` / `is_traditional` / `is_ascii_punct` 做成了 C 结构体的固定字段，所以它的 API 里**焊死了这五个概念**。我们按名字访问，方案可以自由增删。

## 4. 组件 trait（骨架）

四个骨架，对应 RIME 的四类零件。**签名基本照抄 RIME——它这块设计得好。**

```rust
/// 处理器的可变工作区。它是会话内部状态的**受控视图**：
/// 处理器只能通过它改输入串、光标、开关，不能碰词库或别的东西。
pub struct SessionState {
    pub composition: Composition,
    pub options: Options,
}

/// 处理器：决定"这一下按键算不算输入"。
pub trait Processor {
    fn process(&mut self, state: &mut SessionState, key: &Key) -> ProcessResult;
}

/// 切分器：把输入串切成若干段。
pub trait Segmentor {
    /// 从当前位置继续切分。
    /// 返回 `false` 表示"切分到此结束，后面的切分器不必再看"。
    fn proceed(&self, q: &Query<'_>, seg: &mut Segmentation) -> bool;
}

/// 翻译器：为一段输入产出候选。
pub trait Translator {
    /// 候选写进 `sink`，由 sink 负责限流（见 §4.1）。
    fn translate(&self, q: &Query<'_>, span: Span, out: &mut CandidateSink<'_>);

    /// 本翻译器是否负责这个分段（G3）。
    ///
    /// **tag 是"切分器 → 翻译器"的绑定层**：切分器给分段打标签（`abc`、`punct`、
    /// `radical_lookup`…），翻译器据此声明自己管哪一类。一个分段可带**多个** tag。
    ///
    /// 这正是 RIME 让一个方案里能同时挂"拼音 / 英文 / 自定义短语 / 拆字反查"
    /// 四个翻译器的机制——**它们不靠位置区分，靠 tag 区分**。
    fn accepts(&self, _tags: &[Tag]) -> bool { true }
}

/// 兜底翻译器：**保证"你敲的东西永远能上屏"**（G4）。
///
/// RIME 用 `echo_translator` + `fallback_segmentor` 做到这件事。这不是可选功能，
/// 而是输入法的一条**基本安全感**：查不到词时不能什么都不给，否则用户会
/// 以为输入法坏了、或者卡在一个无法退出的输入状态里。
///
/// 实现上它通常是流水线里**最后**一个翻译器，产出一个 `Origin::Literal`
/// 的候选（文本就是原始输入），分数取 `Score::FLOOR` 之上一个很小的值——
/// **分低，但一定在**。
pub trait Fallback {
    fn fallback(&self, q: &Query<'_>, span: Span, out: &mut CandidateSink<'_>);
}

/// 滤镜：对候选列表做后处理（去重、纠错、简繁、标点、置顶）。
pub trait Filter {
    fn apply(&self, q: &Query<'_>, span: Span, cands: &mut Vec<Candidate>);
    /// 默认对所有段生效；实现可限定只对某些 tag 生效。
    fn applies_to(&self, _tags: &[Tag]) -> bool { true }
}

/// 格式化器：对**显示字符串**做重写（`preedit` / `comment` 的格式）。
///
/// 与 `Filter` 的区别：`Filter` 改的是**候选列表**，`Formatter` 改的是
/// **一段文字怎么显示**。两者作用对象不同，故是两个类别。
///
/// **这是 v2 初稿漏掉的一个类别。** RIME 有它（`formatter.h`，用于
/// `preedit_format` / `comment_format`），而初稿只说了"棱镜的投影规则
/// 在运行时会复用于显示"，却没给它一个 trait——于是"方案里怎么配置
/// 显示格式"这件事在设计中无处安放。
pub trait Formatter {
    /// 就地把 `text` 改写成要显示的样子。
    fn format(&self, q: &Query<'_>, text: &mut String);
}
```

> **四个骨架是刻意的分类，不是随手划的**：RIME 的实际组件也落在这几类里（处理器 / 切分器 / 翻译器 / 滤镜 / 格式化器）。**分类本身就是内核的一部分**——增加第五个类别需要改内核。这是诚实承认的边界，见 §2.5。

### 组件如何拿到服务：注入，而不是穿过 `Query` 🔴

**这是 DSH（DeepSeek Harness）架构里最值得抄的一条**（`dshsrc/docs/architecture.md`）：

> "A **seam** is a swappable capability with three roles: a **Service Definition** declaring the interface, a **Service Provider** implementing it, and a **Consumer** using it. …… **one role alone is not a seam; adding a capability means designing all three**."

对应到我们：

| 角色 | 我们这里的形态 | 例子 |
| --- | --- | --- |
| **服务定义** | `stele-core` 里的 trait | `Lexicon`、`Ranker`、`MemoryStore`、`Clock` |
| **服务提供者** | 实现该 trait 的类型（可来自零件包） | 内存词库 / mmap 词库；个人 n-gram / 通用预测表 |
| **消费者** | 使用该服务的组件 | 翻译器用 `Lexicon`；重排管线用 `Ranker` |

**规则**：服务在**组件构造时注入**（组件持有 `Arc<dyn Lexicon>` 之类），**不穿过 `Query`**。

```rust
/// 举例：一个持有自己词库的翻译器。
/// 方案想给它挂哪个词库，就在配置里写哪个——**能挂几个是方案的自由**。
pub struct ScriptTranslator {
    lexicon: Arc<dyn Lexicon>,      // 构造时注入，不是每次查询传进来
    algebra: Arc<Projection>,       // 同样是注入的
    config: TranslatorConfig,
}
```

**为什么必须这样**（而不是把服务塞进 `Query`）：

1. **多词典方案**：rime-ice 一个方案挂了 4 个以上词库。`Query` 里只有一个 `lexicon` 字段的写法**表达不了**。
2. **可替换性**：换一个词库实现（内存 → mmap）只需在装配处换一行，组件代码不动。
3. **显式失败**：装配时如果找不到方案要求的服务，**立刻报错**；而不是运行时发现 `Query` 里是空的。
4. **可裁剪**：不装配某个服务，对应组件就不存在，二进制里也可以没有它（服务内存红线）。
5. **注册即"可撤销的效果"**：DSH 的做法是"注册是效果，插件卸载时自动回卷"。这对我们意味着——**切换方案时，上一个方案注册的组件不会泄漏**。

### 4.1 `CandidateSink`：为什么候选用列表而不是流 🟡

```rust
/// 候选的写入缓冲，带**容量上限**。
pub struct CandidateSink<'a> {
    buf: &'a mut Vec<Candidate>,
    cap: usize,
}

impl CandidateSink<'_> {
    /// 超出上限的候选被静默丢弃。
    /// 这保护了引擎不被"某个查询命中几万条词条"拖垮。
    pub fn push(&mut self, c: Candidate) {
        if self.buf.len() < self.cap { self.buf.push(c); }
    }
    pub fn len(&self) -> usize { self.buf.len() }
    pub fn remaining(&self) -> usize { self.cap.saturating_sub(self.buf.len()) }
}
```

拼写层用它写出展开结果：

```rust
/// 一条展开出来的编码切分：编码 + 代价 + 属性。
pub struct Expansion {
    pub code: Vec<CodeUnitId>,
    /// 相对规范拼写的**代价**（对数域，通常 ≤ 0）。
    /// 简拼/模糊音/补全/纠错的"罚分"都在这里，由方案数据给出（§2.4.4）。
    pub cost: Score,
    /// 这条边经过了哪些变形（G9）。
    pub attr: SpellingAttr,
}

/// 展开结果的写入缓冲，同样限流。
pub struct ExpansionSink<'a> {
    buf: &'a mut Vec<Expansion>,
    cap: usize,
}
```

**决策：用 `Vec` + 限流，不抄 RIME 的惰性流（`Translation`）。** 三条理由：

1. **排序天然需要全量。** 候选按分数降序排列，不生成完就没法排序。RIME 的"惰性"实际是**带截断的批量拉取**（`Menu::Prepare(candidate_count)`），不是真正的流式。
2. **惰性引入不确定性。** 拉取时机、截断点、滤镜顺序互相耦合，难以调试。而我们有"可复现"的铁律（PLAN §5.2）。
3. **它解决的问题我们没有。** RIME 的惰性是为超大词库 + 昂贵候选准备的。

**保留退路的方式**：`Translator` 的签名是"写进 `sink`"而不是"返回 `Vec`"。将来真需要流式，只要把 `sink` 换成一个会阻塞/拉取的实现，**翻译器的代码一行不用改**。

**注意一个次序陷阱**：`sink` 的容量是在**去重之前**扣的。如果某个翻译器产出大量重复候选（这在词库有重复词条时很常见），配额会被重复项吃掉。因此**去重应当尽早做**（或在 `sink` 内部按 `(text, span, lane)` 顺手去重），并且 `cap` 要留足余量。这是 P1 就要验证的一点。

**限流上限是必须的**：即使有 mmap，一次查询 `a` 也可能命中上万条。建议默认 `cap = 200`，之后由滤镜裁到候选窗页大小（5–9）。

### 4.2 `Query`：一次查询的只读上下文

```rust
/// 传给所有组件的只读上下文。生命周期参数 `'a` 表示
/// "这些东西活得比本次查询久，你尽管借用"。
///
/// **这里只放"每次查询都不同"的数据，不放服务。**
/// 词库、记忆、时钟等服务在**组件构造时注入**（见 §5.0）。
pub struct Query<'a> {
    pub input: &'a str,
    pub caret: usize,
    pub options: &'a Options,
    /// 最近已上屏的词（最新的在末尾）。
    ///
    /// **`Lane::Predict` 完全依赖它**：预测"下一个词"必须知道"上一个词是什么"。
    /// `Lane::Input` 的翻译器通常忽略它，但上下文重排（P4b）会用。
    /// 长度上限由方案配置（例如只保留最近 8 个词），避免无界增长。
    pub context: &'a Context,
    /// 当前会话的只读状态（用于少数需要看整体状态的组件）。
    pub composition: &'a Composition,
}

/// 已上屏内容的滚动窗口。
#[derive(Clone, Debug, Default)]
pub struct Context {
    /// 最新的在末尾。
    pub recent: Vec<String>,
}
```

**这是一个 v2 初稿的遗漏**：初稿的 `Query` 里**没有任何地方能拿到"刚才打了什么"**，因此下一词预测在数据模型上根本无法实现。RIME 对应的是 `commit_history.cc`。补上之后，P4b 才有落脚点。

**⚠️ 另一处修正（v2 初稿的错误）**：初稿的 `Query` 里有一个 `lexicon: &dyn Lexicon` 字段——**这是"单个词库"的假设被焊进了内核**。而 rime-ice 一个方案里同时挂了 4 个以上词库（主拼音、英文、自定义短语、拆字、中英混合）。单个 `lexicon` 字段**无法表达多词典方案**。

正确做法见本节上文「组件如何拿到服务」：**服务在组件构造时注入**，不用穿过 `Query`。于是一个翻译器可以持有自己的词库，方案想挂几个就挂几个。

### 4.3 候选通道（`Lane`）：让"精确优先"与"下一词预测"同时成立 🔴

D23 的具体化。这是 v2 初稿里**最严重的功能性缺陷**——初稿把"精确优先"实现成"所有非猜测候选必须连续排在所有猜测候选之前"，等于**禁止混排**，因此**任何"把预测词插进候选列表"的功能都不可能实现**。

#### 4.3.1 两条通道的规则

| | `Lane::Input` | `Lane::Predict` |
| --- | --- | --- |
| 回答的问题 | "你正在敲的这串键，想要哪个词？" | "你接下来可能想打什么词？" |
| 例子 | `nihao` → 你好 | 微信 → 朋友圈 |
| 排序 | 严格：全序 + 精确优先 | 宽松：可混排、可插队 |
| 数量 | 由方案定（页大小 × 若干页） | **严格受限**（建议 1–2 个） |
| 参与"盲选"（按数字键选第 N 个） | ✅ 参与 | ❌ **不参与** |
| 铁律"精确优先" | ✅ 适用 | ❌ **不适用** |
| 学习归属 | 按 `input` 记录 | 按 `context` 记录 |
| 可否一键关闭 | 不适用 | ✅ 必须可关 |

**为什么盲选必须排除预测**：用户对 `Lane::Input` 会形成肌肉记忆——"敲 nihao 然后按 1"。如果预测候选也能被数字键选中、还能改变位置，这套肌肉记忆就崩了。**预测可以看，但不应该被"顺手选中"。** 前端点击/触摸选择是另一回事（那是明确意图）。

#### 4.3.2 `Session::candidates()` 返回什么

**返回"已渲染顺序"的单一列表**，即前端照着画就行。规则：

1. 先排 `Lane::Input`（按 §5.4 的严格规则）。
2. 再把 `Lane::Predict` 的候选**插入到方案指定的位置**（默认：紧随 `Lane::Input` 的第 1 名之后）。
3. 两个通道**各自内部**保证可复现；跨通道的位置由配置固定，同样是确定的。

> **这样"可复现"（PLAN §5.2）完好无损**：预测插入的位置是配置决定的常量，不是随机的。

#### 4.3.3 `select(index)` 的索引空间

**索引指向"已渲染列表"的位置**（即 `candidates()` 返回的那个列表），两条通道统一编号。

**但 `index` 落在 `Lane::Predict` 上时必须满足其一**：
- 该次调用来自**明确的指针/触摸选择**（前端传 `Selection::Pointer`），或
- 方案显式允许预测候选被编号选中（默认**不允许**）。

```rust
/// 选中的来源。用于区分"键盘盲选"与"明确点选"。
pub enum SelectionSource {
    /// 键盘数字键 / 空格 —— 盲选，受肌肉记忆约束。
    Keyboard,
    /// 鼠标点击 / 触摸 —— 明确意图，可以选中预测候选。
    Pointer,
}
```

**理由**：这是"预测不参与盲选"这条规则的执行点，与 §5.3 的断言属于同一类——**铁律必须落在某个具体的 API 上，否则它只是一句话**。

#### 4.3.3b 落地时补的两条（P4b 实测，**不改变上面的语义**）

本节前面把两条要求分别写下时，没有注意到它们的**交点**：

- §4.3.2：预测插在 `Lane::Input` 的第 1 名**之后**（可配置的位置）；
- §4.3.3：`index` 指向**已渲染列表**中的位置。

两条同时成立时，插进来的预测会把**后面所有输入候选的编号整体推后**：
用户按 `2`（肌肉记忆里"第 2 个词"）命中的是一条预测，而预测不参与盲选
——表现为"按了没反应"。这恰好破坏 §4.3.1 要保护的那件事（见 PLAN **D44**）。

**补的第一条：两个编号空间显式换算一次。**
数字键数的是"**第 N 个输入候选**"，换算在
[`SessionState::selectable_index`] 一处完成（`predict_start` / `predict_count`
由流水线在 `compose` 里写回）。`select(index, ..)` 的**公开**语义不变——
它仍然是"已渲染列表的下标"；变的只是 `selector` 产生那个下标的方式。
于是插入位置可以自由调整，而输入候选的编号恒定。

**补的第二条：输入为空时也要产出预测。**
"下一词预测"的**主场景**恰恰是"刚上屏完一个词、还没敲下一个键"——
那一刻 `Composition::input` 是空的。若 `compose` 在输入为空时直接返回空列表，
这条能力在会话层就永远看不见（`Session::candidates()` 永远是空的）。
因此 P4b 起：**输入为空仍然走预测那一条路**，只是没有 `Lane::Input` 候选。
上屏之后会话会立刻重算一次（`SessionImpl::finish_commit`），
于是"刚打完『今天』就能看见『天气』"。

> 两条都不改语义与不变式，只把"语义在实现里到底落在哪一行"写清楚。
> 预测候选的 `Origin` 是新增的 `Origin::Prediction`——它既不是造句，
> 也不是词库命中，UI 与 `--candidates` 都该把它分开显示。

#### 4.3.4 与 RIME 的对比

RIME 的 `librime-predict` 把预测**混在同一张候选表**里，因此不得不加两个补丁式的配置：`max_iterations: 1`（防止无限连续预测）、`max_candidates` 必须对齐页大小（"so that period doesn't trigger next page"）。**那是没有通道概念时的症状。** 分成通道之后，这两条都不需要了。

## 5. 服务 trait（外部资源）

按 PLAN §2.5：**外部资源一律通过 trait 注入**，引擎不直接读文件、时钟或网络。

```rust
/// 编码单元的编号。编码字母表在加载方案时建立，之后热路径上统一用整数传递，
/// 避免反复比较字符串。
///
/// **通用类型**：拼音方案下每个编号对应一个音节（`ni`、`hao`）；
/// 仓颉方案下每个编号对应一个字母（一个字根）。引擎不关心是哪种。
/// （RIME 源码里这个类型叫 `SyllableId`，见 §1 的术语对照。）
#[derive(Clone, Copy, PartialEq, Eq, PartialOrd, Ord, Debug, Hash)]
pub struct CodeUnitId(pub u32);

/// 某方案允许出现的全部编码单元，负责"拼写 → 编码"的转换。
/// **它的内容是方案数据**（拼音方案的音节表 / 仓颉方案的字母表），
/// 引擎里不内置任何一份。
pub struct CodeAlphabet { /* 加载方案时构建 */ }

/// 词库：把编码映射到词条。P1 用内存实现，P2.5 换成 mmap 实现，引擎代码不动。
///
/// **精确匹配**：变体拼写（简拼 / 模糊音 / 补全 / 纠错）已经在棱镜那一层
/// 被展开成不同的编码，到这里就已经是确定的一条编码了（§5.2）。
///
/// **一个方案可以装载多个词库**，每个词库注入到需要它的那个翻译器
/// （rime-ice 就挂了 4 个以上）。"引擎里有几个词库"是方案的自由。
pub trait Lexicon: Send + Sync {
    fn lookup(&self, code: &[CodeUnitId], out: &mut CandidateSink<'_>);
}

/// 拼写层（棱镜）：把**用户敲出来的拼写**映射到**编码**，并给出代价与属性。
///
/// **为什么它与 `Lexicon` 必须分开（G2）**：RIME 允许两者独立替换——
/// 双拼方案的经典做法是「**用全拼的词库，只换拼写规则**」
/// （`reverse_lookup` 就有独立的 `dictionary` **和** `prism`）。
///
/// 旧设计把 `alphabet()` 放在 `Lexicon` 上，等于宣称"换拼写就必须换词库"，
/// **把两个可以自由组合的东西焊死了**。
///
/// 另外 RIME 的 `speller/algebra` **只作用于拼写法**（有效拼写集合 → 编码集合的映射），
/// 从不作用于词条本身——所以它属于这一层，不属于词库层。
pub trait Spelling: Send + Sync {
    /// 编码字母表。拼音方案约 400 个音节；仓颉方案 24 个字母。
    fn alphabet(&self) -> &CodeAlphabet;

    /// 把一段拼写展开成所有可能的编码切分（带代价与属性）。
    ///
    /// 这是**通用最短路算法**的输入：简拼/模糊音/补全/纠错在这里变成
    /// "带代价的边"，而引擎并不认识这些名字（§2.4）。
    fn expand(&self, spelling: &str, out: &mut ExpansionSink<'_>);
}

/// 重排器：P4a 的记忆、P4b 的上下文、P5 的向量都实现它。
pub trait Ranker: Send + Sync {
    /// 允许改分、允许重排；**不允许凭空生成候选**（PLAN §5.3），
    /// 也不允许在 `Lane::Input` 内把非猜测候选排到猜测候选之后（§5.3 的断言）。
    fn rerank(&self, q: &Query<'_>, cands: &mut Vec<Candidate>);
}
```

### 5.1 数据源 trait

引擎**不碰文件、时钟、随机数**：

```rust
pub trait Clock: Send + Sync {
    /// Unix 时间戳（秒）。P4a 的时间衰减需要它。
    fn now_secs(&self) -> u64;
}
```

测试时注入一个"时间定格"的实现，就能稳定测试衰减逻辑。

### 5.2 为什么 `Lexicon` 保持精确匹配（变体拼写不放这里）🔴

> 本节内容与 §2.4.4 是同一件事的两面：**变体拼写（简拼、模糊音、补全、纠错）在方案数据里声明，由通用编译器烘进棱镜；运行时词库只做精确查找。**

RIME 的关键做法（值得照抄）：

> **RIME 不在运行时做模糊查词。它在部署期就把 `nh` 这类缩写当成合法的"拼写"生成出来，存进棱镜。**

于是运行时词库永远是**精确查表**，复杂度全部落在棱镜的边上——每条边有一个**类型**和一个**代价**：

| 边的类型 | 代价（对数域） | 对拼音方案的含义 |
| --- | --- | --- |
| `Normal` | 0 | `ni hao` |
| `Fuzzy` | 0 | 模糊音：`z` ↔ `zh` |
| `Abbreviation` | 小额，待实测 | 简拼：`n h` ← 每个音节取首字母 |
| `Completion` | `ln(0.05) ≈ -3.0` | 补全：`niha` → `nihao` |
| `Correction` | `ln(0.01) ≈ -4.6` | 纠错：打错的音 |

**注意上表的左列对引擎而言只是"边的类型编号"**，右列才是拼音方案赋予它的意义。引擎不认识"简拼"这个词（§2.4.5 的命名检查会拦住它）。

**结论**：

- 变体拼写**不进 `Lexicon`**；规则的**声明**在方案 YAML 里，**编译**由通用编译器完成，**运行**由通用切分器在图上走最短路。
- `Candidate.attr` 里的 `ABBREV` / `FUZZY`（等等）只是"这条边的类型"的体现，分数已被边的代价扣过，因此**非猜测的候选天然排在前面**，无需额外规则。
- **不需要任何模糊查找数据结构**，`Lexicon` 的实现可以简单到一次前缀树查找。
- **仓颉 / 五笔这类不需要变体拼写的方案，棱镜可以只有 `Normal` 边，甚至完全不使用棱镜**（走 §2.4.3 的精确编码翻译器）。

### 5.3 把铁律写成断言：它约束的是**重排器**，不是基础排序 🔴

PLAN §5.4 要求"精确匹配不得被猜出来的候选压过"。**这句话必须是代码，不是文档。** 但先要说清它到底在说什么。

#### 5.3.0 先纠正一处自相矛盾（v2 初稿的错误）

初稿在这里写了一个断言：**"所有非猜测候选必须排在所有猜测候选之前"**——一个**分区**。

而 §5.4 的排序规则是：**① `score` 降序 → ② `Origin` 优先级（平局时）→ ③ 插入序**。

**这两条不可能同时成立**：如果一个造句候选的分数**高于**一个冷门精确匹配词（这在真实词库里很常见——`1` 权重的生僻字 vs 高概率的常用组合），那么按 §5.4 它就该排在前面，而按初稿的分区断言它不许排前面。

初稿实际上是在要求"**生僻字永远压过高概率组句**"，**这会明显损害输入质量**，而且它对 RIME 的真实行为也是不准确的（RIME 按 `quality` 排序，不做这种分区）。

**这条铁律真正要管的是什么？** 回到它的出处——v1 的原话是：

> **AI 只做重排**，绝不凭空生成候选，也**绝不压过精确匹配**。

**主语是 AI（重排器）。** 它约束的是**重排器造成的改变**，不是基础排序的天然结果。也就是说：

> **重排器不许把"猜出来的"候选，顶到"不是猜的"候选前面去。**
> 如果那个猜测候选**本来就**排在前面（因为分数本来就高），那不关重排器的事。

#### 5.3.1 精确的断言：禁止重排造成的**跨类倒置**

```rust
/// 校验"精确优先"这条铁律。
///
/// PLAN §5.4 要求"精确匹配不得被猜出来的候选压过"。主语是**重排器**——
/// 因此这里校验的是"**重排前后**跨类的相对次序有没有被翻转"，
/// 而不是"最终列表里两类必须分区"（分区会损害质量，见 §5.3.0）。
///
/// **作用域**：只对 `Lane::Input` 生效；`Lane::Predict` 不受此约束（§4.3）。
///
/// `is_exact` 的定义在 §3.3——**全项目只有那一处**。
#[cfg(debug_assertions)]
fn assert_no_cross_class_inversion(before: &[Candidate], after: &[Candidate]) {
    // before / after 是同一批候选（按文本即可对应），只是顺序不同。
    // 对每一对"重排前 exact 在前、guessed 在后"的候选，
    // 重排后不允许反过来。
    for (i, a) in before.iter().enumerate() {
        for b in &before[i + 1..] {
            let was_ok = is_exact(a.origin, a.attr) && !is_exact(b.origin, b.attr);
            if !was_ok { continue; }
            let pos_a = after.iter().position(|c| c.text == a.text);
            let pos_b = after.iter().position(|c| c.text == b.text);
            debug_assert!(
                matches!((pos_a, pos_b), (Some(pa), Some(pb)) if pa < pb),
                "重排器把猜测候选 {} 顶到了精确匹配 {} 之前",
                b.text, a.text,
            );
        }
    }
}
```

> **注意这个断言的演化史（三个版本）**：
> 1. v2 初稿：没有 `lane` 过滤，作用域是"整个候选列表"，而且**要求分区**——**与 D23 的下一词预测冲突，且与 §5.4 的排序规则冲突**。
> 2. 第二版：加了 `lane` 过滤，但**仍然是分区**——冲突只解决了一半。
> 3. 现在：**改成"禁止重排造成的跨类倒置"**——这才对上 v1 那句话的主语。
>
> **教训**：一条铁律要写清楚**是谁的约束**（主语）、**管哪一段流程**（作用域）、**允许什么**（边界）。三者缺一，它就会变成绊脚石或空话。

#### 5.3.2 光有 debug 断言不够：需要"单调守卫"

`debug_assert` 在发布构建里**不存在**——发布版里一个写错的重排器照样能把候选顶上去。

DSH 有一个更好的模式叫 **monotonic guard**：一个**最终的、任何后续步骤都无法撤销**的否决。

我们的做法是**回退**而不是分区：

```rust
/// 最后一道守卫：如果重排器造成了跨类倒置，就**整体丢弃它的贡献**，
/// 回退到重排前的基础顺序。
///
/// 为什么是"回退"而不是"分区"：分区会改变基础排序的语义（§5.3.0），
/// 而回退只取消"重排器这一次的作用"——**最坏情况退化成没有重排器**，
/// 永远不会比基础顺序更差。这就是"单调"的含义。
fn guard_precision(base_order: Vec<Candidate>, ranked: Vec<Candidate>) -> Vec<Candidate> {
    if has_cross_class_inversion(&base_order, &ranked) {
        // 发布版：静默回退 + 记一条诊断（供开发者发现自己的重排器有问题）
        log_guard_trip();
        return base_order;
    }
    ranked
}
```

**成本与一个被测试推翻的论断**

本节最初写着"用 O(n) 的单调量替代 O(n²) 检查"，并声称"只要上界足够小，跨类倒置就构造上不可能"。**写 P0 的测试时，这两句话都被证伪了**（`crates/stele-core/tests/invariants.rs`）。

**证伪一：加成上界不足以消除倒置。**
上界 `L` 只保证"猜测候选最多升 `L`"。若某精确匹配的基础分是 `900`、某猜测候选是 `100`、`L = 2000`，那么猜测候选可以合法地升到 `2100` —— **照样压过精确匹配**。

> 要靠算术**完全**消除倒置，只有"给非猜测候选一个类别偏置"一途——而那正是 §5.3.0 否决掉的分区方案（它会损害排序质量）。
> **所以守卫不是可选项。** 上界的作用是"限制移动幅度"，不是"消除倒置"。

**证伪二：O(n) 的检查需要一个目前还不存在的字段。**
精确判据是"对每个猜测候选，**重排前在它之前**的精确匹配数，必须等于**重排后**在它之前的精确匹配数"。要在 O(1) 内知道一个候选在 `before` 里的位置，需要**身份**，而不是按文本线性查找（那就是 O(n²)）。

**因此记入待办（PLAN §6）**：给 `Candidate` 加一个显式的**插入序号** `seq: u32`，由 `CandidateSink::push` 递增分配。它一次解决两件事：

1. **守卫变 O(n)**：用 `seq` 建前缀计数，一次线性扫描即可判定。
2. **平局规则不再依赖"排序是稳定的"**这一隐含性质——`seq` 把"插入顺序"从**实现细节**变成**数据**。

> 这本身是个好教训：**"依赖排序稳定性"是一种隐式契约**，而把序号写进数据是显式的。符合本项目"宁要显式"的一贯取向。
> 在 `seq` 落地之前，守卫只能用于 debug 构建与测试。

**三道防线一起用**：`debug_assert`（开发期**吵**，让人知道哪个重排器写错了）、守卫（发布期**兜**，最坏退化成"没有重排器"）、以及加成上界（**限制**损害幅度）。

> **"结构保证优于运行期修正"这句话仍然成立，但要精确**：
> 上界是"损害有界"，守卫是"做了也会被撤销"，断言是"做了会被发现"。三者**不可互相替代**。

### 5.4 排序：必须是全序 🔴

**排序规则（必须显式实现，不得依赖容器遍历顺序）**

**`Lane::Input` 内：**

1. `score` 降序。
2. 平局时：`Origin` 优先级——即 `Origin` 的**声明顺序**（§3.3）：
   `UserWord > SystemWord > Literal > Sentence`
3. 再平局：**按插入顺序**（使用稳定排序）。

**`Lane::Predict` 内：**

1. `score` 降序。
2. 平局时按插入顺序。
3. **不受 `Origin` 优先级与"精确优先"约束**（它们在这里没有意义）。

**跨通道**：由方案配置决定预测候选插入的位置（§4.3.2），是一个常量，因此整体仍然可复现。

**为什么必须全序**：词库里同权重的词极多（rime-ice 里大量词条权重都是 `1`）。若用 `HashMap` 的遍历顺序决定先后，**同一个输入每次运行的结果可能不同**——直接违反 PLAN §5.2 可复现。

**实现要求**

- 用**稳定排序**（Rust 的 `sort_by` 是稳定排序，`sort_unstable_by` 不是）。
- 引擎内部任何集合，**凡是其顺序可能影响输出的，一律用 `BTreeMap` / `BTreeSet` 或 `Vec`，禁止 `HashMap` / `HashSet`**。
- 🔴 **"插入顺序"本身也必须是确定的**：这一条常被忽略。它要求
  - 翻译器/滤镜的**执行顺序固定**（流水线顺序，已满足）；
  - 每个翻译器**推入候选的顺序确定**——若它遍历一个 `HashMap` 来产出候选，不确定性的源头只是从排序阶段**前移**到了产出阶段，铁律照样被破坏。
  - 因此：**组件内部若需遍历映射，必须用有序容器**。这条要写进组件开发规范，并有测试兜底。
- 加一个测试：同一输入连续跑 100 次，候选序列必须逐字节一致。

#### 5.4.1 排序**在什么时候**发生：必须在滤镜之前 🔴

这一条曾经写错，代价是**四个零件完全不生效**（HANDOFF §5 第 38 条）。

管线的顺序只有一种是对的：

```text
翻译 → 重排（只加分，要参与排序）→ 排序 → 滤镜（按位置表达意图）
```

**为什么排序必须在滤镜之前**：`long_word_filter` 的配置是
「把 2 个词提到**第 4 位**」——它用**位置**描述意图。因此它看到的必须是
最终顺序，而它排出来的顺序**就是**最终顺序，后面不能再排一次。

原先的实现是 `翻译 → 滤镜 → 重排 → finalize(排序)`。那次排序把滤镜的
重排**原样抹掉**：声明 `long_word_filter` 的方案，输出仍是纯粹的权重序
（实测），而装配报告一切正常——正是本项目最恨的那个形状。

**因此 `Pipeline::finalize` 这个钩子被删掉了**：留着它，下一个人就会想
往里放"收尾排序"，而那正好会重新踩上同一个坑。**最终顺序是
`compose` 的契约的一部分。**

> **它为什么长期没被发现**：默认方案与 P3 的测试方案**都没有声明这四个
> 滤镜**，而它们的单元测试直接调 `apply()`、**绕过了整条管线**。
> 又一次"接线在、但没被走到"——只不过这次线接错了地方。

### 5.5 候选合并与去重：保留哪个 `Origin` 🟡

同一个候选文本可能来自多个来源（例如「你好」既是词库精确匹配 `SystemWord`，又出现在造句结果 `Sentence` 里）。去重后必须留下**一个** `Origin` 与**一个** `SpellingAttr`，规则：

> - `Origin`：**保留优先级最高的那个**，即按声明顺序取最小值（`UserWord` 最优，`Sentence` 最差）。
> - `SpellingAttr`：**取交集（按位与）**——只有当**所有**来路都是规范拼写时，合并结果才算规范拼写。
>   - 理由：合并后的候选只要有一条来路经过了变形，它就不是"确定无疑的精确匹配"，不该被当作精确匹配对待。

**为什么必须写明**：如果实现时"先到先留"，那么保留哪个取决于翻译器的执行顺序——结果虽然可复现，却**不为任何人有意义地控制**；而 `Origin` 与 `SpellingAttr` 直接决定平局排序、UI 标记与学习主键。这是一个必须在实现前定死的语义。

参考 RIME 的做法：它用 `UniquifiedCandidate` 把被合并的候选挂在 `item` 上，并没有明确"保留谁的 quality"。我们显式定规则。

### 5.6 错误策略：加载期响亮，但**绝不阻止打字** 🔴

引擎的组件 trait（`Processor` / `Segmentor` / `Translator` / `Filter` / `Formatter` / `Lexicon` / `Ranker`）**都不返回 `Result`**。这是刻意的：

> **所有可预期的错误都在"加载时"暴露；运行期不可失败——失败即 bug。**

理由：

- 按键路径（P99 < 10 ms）上不应该有错误分支与错误传播，那会污染每一个热路径签名。
- 输入法在打字中途"报错"没有合理的用户体验——前端无法处理，用户也无从修复。
- 配置错误、词库损坏、方案字段缺失**全部是加载期问题**，必须**一次报完**而不是遇到第一个就返回（对应 D17 的"零件自描述配置"）。

**⚠️ 但加载期报错 ≠ 拒绝启动。** 这是本设计最初写错的一点，纠正如下：

> **一个配置笔误绝不能让输入法无法启动——否则用户连"打字去改配置"都做不到。**

这是输入法与普通程序的根本差别：**它的失败是自锁的**。一个把 `translators` 写错一个字母的用户，如果输入法拒绝启动，他就只能在别的设备上搜索解决办法。

因此启动策略是**降级而不是中止**（借鉴 DSH 的反面教训：DSH 的 `assertEntriesActivated` 会让一个坏插件中止整个启动——那是调试良好的开发工具的合理选择，**不是输入法的**）：

| 情形 | 行为 |
| --- | --- |
| 基准方案损坏 / 缺失 | 回退到**内置最小方案**（保证能打字） |
| **用户补丁**有错 | **保留上一份可用配置**，丢弃出错的补丁层，**弹出可读诊断** |
| 某个可选零件缺失 | 该零件不生效，其余照常（显式可选读取） |
| 词库编译产物校验和不匹配 | **拒绝该产物**（不是"凑合用"），回退上一份可用产物并提示重新部署 |
| 方案要求的**必需**零件缺失 | 该方案不可用，列出缺什么；**但不影响其他方案** |

**三条配套要求**

1. **`Engine` 的构造函数返回 `Result`**，且一次报出全部问题；但**调用方（CLI / 前端）的默认行为是降级 + 提示**，不是退出。
2. **保留上一份可用配置**（last-good）：写入新配置前不销毁旧的；新配置校验失败就回滚。
3. **诊断要可读且可定位**：说清"哪一层、哪个条目 id、哪个字段、期望什么"。

**与方案切换的关系**：因为方案之间互不依赖（§2.5），**一个方案坏掉不影响另一个**——用户总能切回默认方案打字。

### 5.7 按键路径上不许有事件总线 🔴

DSH 用事件瀑布（waterfall）做扩展点，作者自己承认：**"瀑布 + 广播不如直接调用直接……代价是多了一套要学的事件词汇"**（`reference/dsh-plugin-architecture-lessons.md`）。

它那边每次**工具调用**走一遍瀑布是可以的；**我们每一次按键都要走**，不行。

**规则**：扩展点的**装配在加载时完成**——方案解析后得到一个**静态化的流水线描述**（一个 `Vec<Box<dyn Component>>` 或索引表），按键时**按固定顺序直接调用**，不做事件分发、不做字符串查找、不做遍历匹配。

**代价对比**：动态分发（trait 对象虚调用）在本项目的量级下无关紧要（约 1 ns）；**但一个事件总线是数量级的问题**。所以：

- ✅ 允许：固定顺序 + trait 对象虚调用
- ❌ 禁止：按键路径上的事件广播、字符串名字查表、遍历所有注册项找"谁能处理"

## 6. 方案与配置（D17 / D24）

- 零件按**名字**注册在注册表里；方案只是**选择并配置**零件的声明式数据（YAML）。
- 每个零件**自描述参数**：参数名、类型、默认值。加载配置时一次性校验，报出可读错误。
  - 反例（RIME）：配置写错字段名会被静默忽略，然后行为诡异。
- 零件**可裁剪**：不使用的能力不应被编入二进制（服务内存红线）。
- 零件是**编译期 / 原生扩展**，不是运行时脚本沙箱（D16）。
- 保留"方案 / schema"这个面向用户的词——它是 Rime 生态的通用概念。

**为什么这直接服务内存目标**：RIME 是单体——不管方案用不用，Lua、OpenCC、LevelDB 全部编进二进制并加载。零件可插拔后，一个只要拼音的输入法可以只编入 4 个零件。

### 6.1 三层能力模型（借鉴 DSH，但不是照抄）

DSH 的 `architecture.md` 给了一个比 RIME 更清晰的模型，我们**按输入法的需要重新裁剪**后采用：

| DSH 的概念 | 我们的对应物 | 说明 |
| --- | --- | --- |
| **Service Definition** | `stele-core` 里的 trait | 服务接口 |
| **Service Provider** | 零件包里的实现 | 词库、重排器、存储 |
| **Consumer** | 用它的组件 | 翻译器、重排管线 |
| **bundle**（配置行 + 其挂载的代码，可被上层补丁） | **方案包** | 一份方案 YAML + 它需要的零件 |
| **profile**（命名的组合 + 用户的 patch 文件） | **用户配置** | 用户选择启用哪些方案、写了哪些补丁 |
| **patch 按行 id 定位** | **按条目 id 补丁** | 见 §6.2 |

DSH 那句关键的话值得原样记住：**"一个角色不成其为 seam；增加一个能力意味着把三个角色都设计出来。"** 这比"写个插件"要求更高——**你必须同时说清接口是什么、谁实现、谁消费**。

#### 6.1b 一处**故意不抄**：装配顺序 vs 执行顺序

DSH 的 `bundle/base/cordis.patch.yml` 里有一句：**"row order carries no load semantics (activation is service-availability driven)"**——行序不承载语义，激活由"服务是否可用"驱动。

**这句话对一半，我们不能全抄**：

| | 顺序由什么决定 | 为什么 |
| --- | --- | --- |
| **装配 / 初始化顺序** | **依赖驱动**（A 要的词库先就位） | 抄 DSH：避免"必须把词库那行写在前面"这种隐式约束 |
| **执行顺序（流水线）** | **方案显式声明**（就是列表顺序） | **绝不能抄 DSH**：对我们的流水线，顺序**本身就是语义**——**滤镜顺序决定结果** |

**证据（第一手实测）**：rime-ice 的配置里明确写着顺序要求——`pin_cand_filter > emoji > 简繁`、`long_word_filter > emoji`。**把"置顶"放在"加 emoji 候选"之后，置顶就会被挤掉。** 顺序错了功能就错。

所以我们的规则是：

> **零件"怎么被装起来"由依赖决定；零件"按什么顺序跑"由方案明文写死。**

DSH 可以不在乎行序，因为它的事件监听器是**无序广播**；我们的滤镜是**有序变换**，两者本质不同。**这就是"不要照抄"的具体含义——借它的抽象，不借它的假设。**

### 6.2 配置分层与补丁：比 RIME 的 `*.custom.yaml` 更稳的做法 🔴

RIME 的补丁用**斜杠路径 + 位置**定位：

```yaml
patch:
  'engine/translators/@before 0': predict_translator   # ← 依赖"位置"
```

**这很脆弱**：基准方案一旦增删条目，位置就变了，用户的补丁会静默失效或错位。

我们的做法（借鉴 DSH 的"按行 id 定位"）：

```yaml
# 基准方案里每个流水线条目都有稳定 id
engine:
  translators:
    - id: main          # ← 稳定标识，不是位置
      type: script_translator
      dictionary: main
    - id: emoji
      type: simplifier
```

用户补丁只写差异，**按 id 定位**：

```yaml
# 用户的补丁
patch:
  - target: translators/emoji        # 按 id 定位，与位置无关
    set: { enabled: false }
  - insert_after: translators/main    # 需要插队时才用位置
    value:
      id: predict
      type: predict_translator
```

**分层顺序**（后层覆盖前层）：

1. 方案包的基准配置
2. 方案包内部的层
3. **用户的补丁文件**
4. 命令行临时覆盖（`--patch`）

#### 6.2.0 跨文件节点复用（G1：我们**必须补**的能力）

RIME 有一项我们最初漏掉的能力：**在一个配置里引用另一个文件的某个节点**。

```yaml
# 方案里复用全局默认的标点表——不抄一遍，而是引用
punctuator:
  __include: default:/punctuator
key_binder:
  __include: default:/key_binder
```

rime-ice 大量使用它（`punctuator: __include: default:/punctuator`、`key_binder` 导入）。
**没有它，每份方案都要把标点表、按键绑定整段重抄一遍**——这是方案作者的主要摩擦之一。

**我们的等价设计**

```yaml
# 引用另一个文件的节点
punctuator:
  $ref: "default:/punctuator"
# 也可以引用后只改一处（引用 + 补丁）
key_binder:
  $ref: "default:/key_binder"
  $patch:
    bindings/+:
      - { when: paging, accept: comma, send: Page_Up }
```

**求值顺序遵循 RIME 的固定规则**（作者文档原文）：

> 「同一節點下，編譯指令的執行順序爲：`__include:` 包含指定節點 → 合併當前節點下的其他 key-value 數據 → `__patch:` 修改子節點。」

**并且顺序由引擎写死，不由书写顺序决定**——因为 YAML map 的 key 是无序的：

> 「由於 YAML map 的 key 是無序的，**書寫順序並不決定編譯指令的先後**。」

**三条实现约束**

1. **被引用的节点永不被修改**（RIME 也是这么保证的）——`$ref` 是复制语义，不是别名。
2. **检测循环引用**并在加载期报错（不是栈溢出）。
3. **可选引用**：目标不存在时不报错（对应 RIME 的 `?` 后缀，见 G7）。

#### 6.2.1 RIME 的 `*.custom.yaml` 到底缺什么

DSH 有两套覆盖机制，而**它的"设置"那一套恰好补上了 RIME 的全部缺口**（`reference/dsh-plugin-architecture-lessons.md`）：

| 能力 | RIME `*.custom.yaml` | DSH 的设置机制 | 我们要的 |
| --- | --- | --- | --- |
| 增量覆盖 | ✅ | ✅ | ✅ |
| **可撤销 / 回到默认**（un-patch） | ❌ 补丁一旦写就回不去 | ✅ `replace({})` 即"重新继承默认" | **必须** |
| **值来自哪一层**（provenance） | ❌ 无从得知 | ✅ 分层可查 | **必须** |
| **写入冲突检测** | ❌ 两个工具同时改会互相覆盖 | ✅ `expectedRevision` + 冲突错误 | **应该** |
| **坏配置不致命** | ⚠️ 部署失败 | ✅ 保留上一份可用值 | **必须**（§5.6） |
| 用户层与基准层分离 | ✅ | ✅ | ✅ |

**这四条缺口就是我们相对 RIME 的"配置性升级"的具体内容。** 不是口号，是四个可验收的行为：

1. **能撤销**：用户删掉补丁 → 立刻回到方案默认，不需要知道默认值是什么。
2. **能溯源**：`stele --dump-config` 对每个值标注**它来自哪一层**（内置默认 / 方案包 / 用户补丁 / 命令行）。
3. **能检测冲突**：外部工具改配置时，版本号不匹配就报冲突，而不是静默覆盖（影响 P8 设置界面的设计）。
4. **坏补丁不致命**：见 §5.6。

**与 RIME 的关键差别**：RIME 的补丁是**单向叠加、不可逆、无出处**；我们是**分层可查、可撤销、有出处**。

### 6.3 注册是"可撤销的效果"

DSH：**"注册是效果，插件卸载时自动回卷。"**

对我们的意义很具体：**切换方案时，上一个方案注册的零件必须被干净卸下**——不能留下还在运行的处理器、还占着内存的词库、还挂着的监听器。这是 §0.2 内存红线在长时间运行下的保障。

实现手段：方案加载时返回一个**句柄**，丢弃它即撤销全部注册（Rust 的 `Drop` 天然适合这件事）。

**并且装载必须是原子的（all-or-nothing）**：DSH 的 `EntryGroup.update` 是全组回滚。我们的方案层应用也一样——**要么整层生效，要么整层不生效**，不能留下"加载了一半"的方案。半加载的方案是最难排查的 bug。

### 6.4 编译产物的完整性、版本与门禁 🔴

#### 6.4.1 产物按内容寻址，校验不通过就拒绝

词库编译产物（表 / 棱镜 / 反查）必须带**内容校验和与格式版本**，加载时验证：

- **校验和不匹配 → 拒绝加载该产物**，回退到上一份可用产物，并提示"重新部署"。
  - ❌ 不做：凑合加载（RIME 用校验和判断**要不要重编译**，但那是构建期的判断；运行期也需要防"用错版本的产物"）。
- **格式版本不认识 → 明确拒绝**，绝不猜测。
- 产物文件名里带内容哈希（`main.<hash>.table`），便于多版本共存与原子替换。

#### 6.4.2 版本门禁：**DSH 的缺口，我们不重复**

这是那份报告里最值得警惕的一条：

> **DSH 没有 per-plugin 的 API 版本或兼容门禁**——`engines.dsh` 只是声明性的，**没有任何读取者**。只有客户端 bundle（内容哈希）和 typert 协议（`version !== 1` 抛错）真正协商。

**它们可以这样，因为插件和宿主一起发布、一起升级。我们不行**：方案是**用户写的、长期存在的**，方案格式会演进，用户的补丁必须能活过升级。

因此我们需要两级版本：

| 版本 | 管什么 | 不匹配时 |
| --- | --- | --- |
| **方案格式版本** | YAML 配置的语法与字段语义 | 用**逐级迁移**（一个迁移只负责一步 `vN → vN+1`，借鉴 DSH）升级；迁不动就明确拒绝并说明 |
| **零件 API 版本** | 零件（原生扩展）的 trait 与参数 schema | 零件声明它支持的方案格式范围；不匹配时**该零件不生效并报错**，不影响其他零件 |

**为什么这直接关联 D24**：如果方案是长期资产，**它的格式就是一份对外契约**。没有版本门禁的"可配置性"，用户不敢投入。

### 6.5 CI 门禁：把原则变成脚本 🔴

DSH 有一个值得学的做法：**55 个 `scripts/verify-*.ts` 检查脚本**，外加一个**构建期纯度门禁**（拒绝跨插件直接 import 值）。**"一切皆插件"不是靠文档维持的，是靠 CI 拒绝违规。**

我们照这个思路，把已经写在文档里的原则变成**真实存在的检查脚本**（P0 建 workspace 时就建起来，不要等）：

| 门禁 | 检查什么 | 对应原则 |
| --- | --- | --- |
| `verify-no-ime-vocab` | `stele-core` / `stele-engine` 的标识符与注释里不得出现拼音/音节/简拼等词 | D20 / §2.4.5 |
| `verify-no-builtin-tables` | 内核 crate 里不得有内置词表/音节表/方案数据 | D20 |
| `verify-no-scheme-data` | `stele-engine` 不得依赖 `schemes/` 下的任何东西，也不得依赖具体方案名 | D24 |
| `verify-no-scheme-depends-scheme` | 方案之间不得互相依赖 | D24 |
| `verify-config-schema` | 每个零件的参数 schema 与文档目录同步（自动生成字段目录） | D17 |
| `verify-missing-docs` | clippy `missing_docs` | §4.8 |
| `verify-deps-license` | `cargo-deny` 许可白名单 | D9 |

**第 5 条顺带解决一个体验问题**：DSH 有自动生成的 `docs/config-catalog.md`（从各零件的 schema 生成）。我们也应该**从零件的参数 schema 自动生成方案字段目录**——这样"方案能配哪些字段"永远和代码一致，不会过期。

## 8. `stele-memory`：用户记忆（P4a ✅）

> **本节在 P4a 之后从"接口预留"改写为"实现说明"**：接口没变
> （`MemoryStore` 的四个方法一字未动），但几条**当时的建议被实测或所有者
> 决定推翻了**——那些结论必须写在这里，否则下一个会话会照着旧文字去改已经对的东西。

**实际实现**（`crates/stele-memory/`，零依赖、无 `unsafe`）：

| 模块 | 职责 |
| --- | --- |
| `decay` | 纯函数：次数 + 时间 → **定点**加成。全程**整数**（D13）：衰减是整数次减半、加成是整数除法 |
| `store` | `MemoryStore` 的实现：`BTreeMap` 全量驻留 + 自写紧凑 KV（魔数/版本/FNV-1a 校验和/原子 `rename`） |
| `ranker` | `Ranker` 的实现：读记忆、按 `bonus_limit` 加分，并且**自己再守一道"精确优先"** |
| `events` | `Learned → record`、`ForgetRequested → forget` 的**唯一**映射点（三个前端共用） |

### 三处与本节初稿不同的结论

1. **键就是"规范编码"（PLAN D42），但算它的地方不是记忆层**。
   初稿写的是"实现必须把 `input` 经 `Spelling` 反查回规范编码"——
   那条路要求记忆实现拿到拼写层与词库，而它们只存在于引擎内部
   （`LoadedScheme`），于是它实际上**走不通**。
   正确做法是**让键随候选一起出来**：翻译器手里本来就有编码
   （`Expansion::code`），把它渲染成键挂在 `Candidate::key` 上，
   上屏时原样带进 `Commit`。于是没有任何一层需要反查，
   而 `nhao` 与 `nihao` 走到同一条编码时**自动**共享记忆。
2. **衰减也是整数**。初稿允许"更新时用浮点，存下来的是定点"。
   实际做法更狠一步：衰减是**整数次减半**（半衰期 30 天），
   于是连那一次浮点都不需要，"跨平台逐位一致"成了类型层面的事实。
3. **上限是 30 000 条，不是 100 000**。实测 +18.2 MiB/10 万条，
   叠上真实词库会越过 30 MB 红线（数字与推导见
   `stele_memory::DEFAULT_CAPACITY` 的文档）。

### 仍然有效的那部分：接口

**接口一字未动**——这正是"先把形状留对"的价值：换成真实现时，
引擎、翻译器、滤镜一行都没改，只多了一个 `Services` 参数。

> **一处对初稿的修正**：初稿的 `MemoryEntry` 里有一个
> `decayed: f32`（"对数域之外的独立量，供 Ranker 自己换算"）。
> 真实现里**没有这个字段**：影响排序的量一律定点（D13），
> 而"衰减成什么样"是记忆实现自己的事，不该漏到公开类型上。
> 公开出来的是 [`Score`] 类型的 `bonus`——**已经可以直接加到候选分数上**。

```rust
/// 一条已学记录。`(输入, 词)` 是主键。
#[derive(Clone, Debug, PartialEq, Eq)]
pub struct MemoryEntry {
    /// **规范编码键**（见 [`MemoryStore::record`]，PLAN D42）。
    pub input: String,
    /// 上屏的文本。
    pub text: String,
    /// 被上屏过几次。
    pub count: u32,
    /// 由"次数 + 时间衰减"算出的**对数域定点**加成，已可直接加到候选分数上。
    pub bonus: Score,
    /// 最后一次使用时间（秒）。
    pub last_used: u64,
}

/// 用户记忆。**P4a 已实现**（`stele_memory::FileMemory`）。
pub trait MemoryStore: Send + Sync {
    /// 记录一次上屏。**必须是异步 / 非阻塞路径。**
    ///
    /// 按 `commit.lane` 分流：`Lane::Input` 用 `input` 作主键，
    /// `Lane::Predict` 用 `context` 作主键（§4.3.1）。
    ///
    /// # ⚠️ 主键必须是**规范编码**（G10 / PLAN D42）
    ///
    /// RIME 明确警告过一颗地雷：
    ///
    /// > 凡是編碼爲源碼表中未出現過的形式，如通過「拼寫運算」實現的**簡拼、異拼**，
    /// > 又如編碼中的**拼寫錯誤**，都將導致該條記錄成爲**用戶詞典中的無效數據**，
    /// > 因爲無法通過正常的輸入檢索到。
    ///
    /// 原因在于**投影是单向的**：词库的键永远是**规范编码**（`ni hao`），
    /// 简拼（`nh`）只是**到达该编码的一条路径**。
    ///
    /// **RIME 的修法是"存规范编码"，我们照做**——只是算它的地方不同：
    /// 不是让记忆实现去反查（那需要拼写层与词库，而它们只在引擎内部），
    /// 而是**让翻译器把编码渲染成键挂在候选上**（[`crate::Candidate::key`]），
    /// 一路带到 [`Commit::key`]。于是
    ///
    /// > `record(commit)` 用的键与 `lookup(candidate.key)` 用的键
    /// > 是**同一个字符串**——"写进去的键一定查得回来"是恒等式。
    ///
    /// 由此还白得一件事：**同一条编码只有一把键**，所以 `nhao` 学到的词
    /// 敲 `nihao` 时照样优先（跨拼法共享），与 rime-ice 功能等价。
    ///
    /// `commit.key` 为 `None` 时（原样上屏、标点、造句）退回按
    /// [`Commit::input`] 规范化：那条路自洽，但不跨拼法共享。
    fn record(&self, commit: &Commit);

    /// 查询某个输入的已学词条，供 `Lane::Input` 的重排使用。
    /// **必须走内存缓存，零磁盘 I/O。**
    fn lookup(&self, input: &str) -> Vec<MemoryEntry>;

    /// **取消一次学习**（G11）。
    ///
    /// RIME 的规则是：「只能夠從用戶詞典中刪除詞組。用於碼表中原有的詞組時，
    /// **只會取消其調頻效果**」——也就是说，"删除"对系统词来说不是删掉它，
    /// 而是**撤销用户对它的加权**。用户需要能反悔。
    fn forget(&self, key: &str, text: &str);

    /// 查询"上一个词之后可能接什么"，供 `Lane::Predict` 使用（P4b）。
    /// 通用 n-gram 表与个人历史可以都在这里返回，由 `score` 区分。
    fn predict_next(&self, context: &Context) -> Vec<Prediction>;
}

/// 一条预测结果（P4b）。
#[derive(Clone, Debug)]
pub struct Prediction {
    pub text: String,
    /// 对数域分数，已与 `Lane::Input` 的分数**可比**（换算责任在这里，不在排序处）。
    pub score: f64,
    /// 来源说明，用于 UI 区分标记（例如"个人习惯" vs "通用搭配"）。
    pub origin: PredictionOrigin,
}

#[derive(Clone, Copy, PartialEq, Eq, Debug)]
pub enum PredictionOrigin {
    /// 来自用户自己的打字历史。
    Personal,
    /// 来自随项目分发的通用搭配表（是数据，不是网络调用）。
    General,
}
```

**来自实测的硬约束**：RIME 的按键延迟 P99 高达 36 ms，**最大的单点瓶颈就是用户词库的磁盘读取**（LevelDB）。因此：

- 用户词库必须**全量放内存**，按键时只在内存里查。
- 改动**异步批量落盘**，绝不阻塞按键路径。

> **P4a 的兑现方式**：落盘只有一条显式入口 `FileMemory::flush()`
> （临时文件 + 原子 `rename`，全量重写而不是追加+合并——理由写在那个方法的文档里）。
> 它不是"少 I/O"，而是**零 I/O**：`crates/stele-memory/tests/no_disk_io_on_keypath.rs`
> 读 `/proc/self/io`，断言 1000 次按键之后 `syscr`/`syscw` 与
> `read_bytes`/`write_bytes` **一个都没涨**。

存储格式参考 RIME 的三元组（可直接借鉴其模型）：

```
key   = 编码 + "\t" + 词
value = 次数 c、衰减值 d、最后使用时间 t
```

只存"次数"是不够的——**没有时间衰减，三年前打过的词会永远霸占第一位**。

## 9. 一次按键的完整旅程

> **本节用一个「拼音方案」举例。** 换成仓颉方案，第 ② 步的切分与组句会消失（走 §2.4.3 的精确编码翻译器），其余流程完全相同——**这正是 §2.4 通用性边界的意义**。

以敲 `n` `i` `h` `a` `o` 再按空格为例。

```
① Key { code: Char('n'), mods: NONE }
   └─ Processor::Speller 处理：state.input = "n"        → ProcessResult::Accepted
   └─ 会话发现输入变了 → compose()

② compose()
   ├─ 切分（Segmentor）
   │    "n" 不是完整音节；但 abbrev 边允许 [n(i)]，惩罚 -1.0
   │    → 得到**一族**带分数的切分，而不只是一条
   ├─ 翻译（Translator，逐段）
   │    Lexicon::lookup([ni]) → 你 / 尼 / 泥 …（score = ln(词权重)）
   │    简拼候选由切分器给出低分，attr = ABBREV
   ├─ 过滤（Filter）：uniquifier 去重
   ├─ 重排（Ranker）：P1 无实现
   └─ 排序：score 降 → Origin 优先级 → 插入序（全序，可复现）

③ 前端读取 candidates() 的前 5 个并绘制
   （此时候选全部属于 Lane::Input——预测通道要到 P4b 才有内容）

④ 继续 i h a o → 切分变为 [ni][hao]
   Lexicon::lookup([ni][hao]) → 「你好」，score = ln(权重)
   同时也给出句子候选（「你」+「好」分开），但分数更低
   → 「你好」排第一

⑤ Key { code: Named(Space) }
   └─ Selector 处理器：选中 index 0
   └─ 返回 Outcome::Committed(Commit {
          text: "你好",
          input: "nihao",
          context: ["我", "要"],      // 已上屏的前几个词
          origin: Origin::SystemWord,
          attr:   SpellingAttr::NORMAL,
          lane: Lane::Input,
          trigger: Trigger::Space,
      })

⑥ 会话调用 MemoryStore::record(&commit)   ← P1 为空实现
⑦ 会话在 drain_events() 中给出 Learned 事件（供前端/日志观察）
⑧ reset()：composition 清空，准备下次输入
```

**注意第 ⑤ 步**：上屏信息是**返回值**带出来的，前端不可能漏读——这就是我们不抄 RIME"布尔 + 读取即清空"的收益。

## 10. 与 RIME 的差异一览

| 方面 | RIME | Stele | 理由 |
| --- | --- | --- | --- |
| 引擎抽象 | `Engine` 一个可变对象 | `Engine`（共享）+ `Session`（私有） | 多客户端、线程安全（D12） |
| 按键返回 | `bool`（消费） | `Outcome` 枚举，带上屏信息 | 防止漏读、保留学习信息 |
| 上屏读取 | `get_commit` 读取即清空 | 返回值直接带出 | 同上 |
| 分数 | 多个字段、部分线性相加 | 单一对数域 `f64` | 可加、可调试（D13） |
| 候选产出 | 惰性 `Translation` 流 | `Vec` + 限流 `CandidateSink` | 确定性、简单（§4.1） |
| 线程模型 | 无全局锁，靠"一会话一线程"约定 | 同上，但由类型系统强制 | Rust 免费获得 |
| 简拼等变体拼写 | 方案 algebra 规则 → 烘进 prism | **同样**：方案声明 → 通用编译 → 通用最短路 | 引擎不含拼音知识（D14 / D20） |
| **下一词预测** | 有（`librime-predict` 插件），候选混在同一张表里 | **有，但走独立通道 `Lane::Predict`** | 混排会破坏盲选肌肉记忆（D23 / §4.3） |
| 开关（选项） | `RimeStatus` 把 `ascii_mode`/`full_shape`/`is_simplified` 等焊成 C 结构体字段 | 全部由方案声明，引擎按**名字**取用 | 否则等于内置输入法知识（D20） |
| 通用性 | 通用，但源码用 `Syllable`/`Syllabary` 等拼音词汇命名（对仓颉是误导） | 通用，且**类型名与注释禁用拼音词汇** | §2.4.5 的命名检查 |
| 翻译器族 | `table_translator`（精确码）+ `script_translator`（拼写图） | **同样两族**，由方案选择 | 仓颉/五笔不需要拼写图（§2.4.3） |
| 配置 | 字符串键，错误静默 | 零件自描述、加载期校验 | 可读错误（D17） |
| 脚本扩展 | Lua 插件 | 不内嵌脚本，原生零件 | 安全 + 可静态分析（D16） |
| 键表示 | X11 keysym | 自有 `Key` 类型，FFI 兼容层 | 前端不必交"Unix 遗产税" |
| 二进制兼容 | 版本化 vtable + `data_size` | 不需要 | 两端都是我们自己的代码 |

## 12. 待验证事项（诚实交代）

1. **简拼的收益 / 成本尚未实测。** 确信它的**规则声明属于方案数据**、**编译属于通用编译器**、**运行属于通用切分器**（§2.4.4）；但"生成一族带代价的切分"会让每次按键的词典查询次数变多。rime-ice 的规则是**每个音节只取首字母**（`abbrev/^([a-z]).+$/$1/`），一族里最多几条路，预计无问题——**但这是 P1 写完后要用数据验证的第一件事**，现在不拍板。
2. **§2.4 的通用性边界还没有被代码验证过。** 目前它是文档上的一条不变式。真正的验收是 §2.4.5 里那个测试：**用同一个引擎 + 一份仓颉（或五笔）方案跑通"编码 → 字"**。在这个测试写出来之前，"引擎不含拼音知识"只是承诺，不是事实。
3. **`Box<dyn Session + Send>` 的虚调用开销**在本项目预算下可忽略（约 1 ns vs 0.5 ms）。但若将来要做"多个引擎并行取并集"，形状可能要改。风险低。
4. **用户词库的并发模型完全未定**（§8 只留了位置），P4a 才有答案。
5. **声调的处理未定**：rime-ice 全库拼音无声调（`nve` / `lve` / `ju` / `qu` 写法），现有设计不含声调。若将来要支持带调输入，需要扩展 `CodeUnitId` 与编码字母表的定义（这是 `Lexicon` 接口内部的事，不会外溢到引擎骨架）。
6. **方案切换（schema switching）尚无设计。** 现在 `Engine` = 一个已加载的方案，但 rime-ice 需要方案选单（RIME 的 `switcher` 是恒定插在最前的处理器）。这既缺 API，也直接影响内存（多方案是否同时驻留）。见 PLAN §6。
7. **方案配置里数值的域尚未定义。** RIME 的 `initial_quality: 1.2` 是加到**线性概率**上的（`exp(weight) + initial_quality`），而我们的 `score` 是对数域。方案配置里的数字按哪个域解释、在何处换算，必须先定，否则 P3 无法与雾凇对齐。
8. **§5.5 的合并规则与 §5.6 的错误策略是本次审阅新定的**，还没有实现验证。
9. **`Context`（已上屏窗口）的长度上限与清理时机未定**，P4b 才有答案；但它是常驻内存，必须计入 §0.2 的预算。
10. **热路径上的分配未做优化，也未测量。** `Composition` 的 `input: String` / `preedit: String` 目前设计成**每次按键重建**。按 §0.2 的预算（P50 < 1 ms）这大概率无妨，但**这是假设，不是测量**——P1 必须用 `stele-bench` 验证，必要时改为复用缓冲区。同类嫌疑还有 `Commit` 每次上屏的 `String` 分配（上屏不频繁，风险低）。
11. **§0.2 的所有数字都是目标**，P1 结束时用实测校正。

## 13. 与 RIME 官方设计文档的对比结论

来源：RIME 作者的完整设计文档（`rime/home` wiki，25 页，已存档于 `.rime-wiki/`），以及三份逐行引用原文的对比报告（`reference/rime-*.md`、`docs/rime-schema-conceptual-model.md`）。

### 13.1 一句话结论

> **Stele 不是在推翻 RIME 的哲学，而是在恢复它。**
>
> RIME 作者 2009 年的原话就是我们的 D20/D24：
> 「**Rime 不是一種輸入法。是從各種常見鍵盤輸入法中提煉出來的抽象的輸入算法框架**……在不同的設定下，Rime 可化身爲不同的輸入法」（`RimeWithSchemata`）
> 「**爲了避免知道得太多，這引擎的內部構造必須精巧**，他存在的意義在於接合內部的各種組件、並對外提供可靠的接口：**Engine 所表達的邏輯僅限於此**」（`RimeWithTheDesign`）
>
> 而 librime 在十幾年的演进中**部分偏离了这个设计**：把 `Syllable`/`Syllabary` 当成引擎词汇（对仓颉是误导）、把五个开关焊进 `RimeStatus`、把关键行为放进 Lua、补丁机制不可撤销也不可溯源。**我们的工作是把它拉回来，并补上它缺的那几块。**

### 13.2 Stele 确实更好的地方（**以作者自己的话为证**）

| # | RIME 的问题 | 证据（作者原文） | 我们的对应 |
| --- | --- | --- | --- |
| 1 | **列表无法增删改单项** | 「對於列表類型，現在無有辦法指定如何添加、消除或單一修改某項，**於是要在定製檔中將整個列表替換！**」（`CustomizationGuide`） | D25：按**条目 id** 补丁 |
| 2 | **位置寻址被作者自己劝阻** | `@before` / `@after` / `@next` 全部标注「**（不建議在補靪中使用）**」 | 同上，位置仅作逃生舱 |
| 3 | 含 `/ + =` 的键**无法寻址** | 「因其在節點路徑中有特殊含義，無法用路徑連寫方式」 | id 寻址不受字符影响 |
| 4 | **无撤销、无溯源、无冲突检测** | 三份报告一致确认：官方文档中 **NOT FOUND**；唯一替代是「**人工对比 `build/` 目录里的编译结果**」 | §6.2.1：可撤销 / 可溯源 / 版本号冲突检测 |
| 5 | 无跨版本配置兼容契约 | **NOT FOUND IN THESE DOCUMENTS** | D27：方案格式 + 零件 API 两级版本门禁 |
| 6 | 词典包**无兼容性检查** | 「目前 librime 並沒有機制保證加載的擴展包與主詞典兼容……**二進制擴展包不宜脫離於主詞典而製作和分發**」（`DictionaryPack`） | D28：内容寻址 + 校验不过即拒绝 |
| 7 | 调试只能**倒推** | 「請對照 `<用戶文件夾>/build/` 文件夾內的編譯結果文件，**檢查配置源文件與補靪**」 | `stele --dump-config`，**每个值标注来自哪一层** |
| 8 | 部署期**静默无输出** | 「編譯新的輸入方案需要一段時間，**此間若無法輸出中文，請稍等片刻**」 | §5.6：降级 + 保留上一份可用配置 + 诊断 |
| 9 | **静默陷阱** | 根节点若用了 `__patch:`，会**静默禁用**自动加载 `.custom.yaml` | 分层显式，不靠隐式约定 |

### 13.3 ⚠️ RIME 更好、我们**确实有缺口**的地方（诚实清单）

这些是这次对比**真正找出来的东西**，不是自我表扬：

| # | RIME 有，我们没有 | 为什么重要 | 处置 |
| --- | --- | --- | --- |

### 13.6 本次对比最有价值的三个发现

**① `Source` 是有损的，必须拆成两个轴（G9）**

RIME 的拼写运算给派生拼写**附加属性**，而且属性**可以叠加**：

> `fuzz/<模式>/<替換式>/`：執行派生運算；派生出的拼寫將獲得「**模糊**」屬性……
> `abbrev/<模式>/<替換式>/`：執行派生運算；派生出的拼寫將獲得「**縮略**」屬性，會在音節切分時與通常的拼寫做區分處理。
> —— `SpellingAlgebra.md`

也就是说：一条边可以**同时**是模糊音**和**简拼。我的 `Source` 是单选题，**这种情形无法表达**——只能任选其一，而且选择是任意的。

**修法**：拆成

```rust
/// 这条编码是怎么被拼出来的——**位集，可叠加**。
#[derive(Clone, Copy, PartialEq, Eq, Debug, Default)]
pub struct SpellingAttr(u8);   // NORMAL | FUZZY | ABBREV | COMPLETION | CORRECTION

/// 候选从哪里来——单值。
#[derive(Clone, Copy, PartialEq, Eq, Debug, PartialOrd, Ord)]
pub enum Origin { UserWord, SystemWord, Literal, Sentence }
```

排序的平局键从两者导出（`Origin` 为主，`SpellingAttr` 只用来判断"是否猜测"）。**这也让 G12（UI 标记）有了数据来源。**

**② 用户词的主键必须是规范编码（G10）**

RIME 的警告是一颗真地雷：

> 凡是編碼爲源碼表中未出現過的形式，如通過「拼寫運算」實現的**簡拼、異拼**，又如編碼中的**拼寫錯誤**，都將導致該條記錄成爲**用戶詞典中的無效數據**，因爲無法通過正常的輸入檢索到。

原因：**投影是单向的**——词库的键永远是**规范编码**，简拼/模糊拼只是"能到达该编码的路径"。

**对我们的直接后果**：P4a 学习时，如果用户是在 `nh`（简拼）下选的「你好」，**不能把 `nh` 当键存**——否则下次在正常路径下检索不到。必须先换算回规范编码 `ni hao`。

**这条如果实现错了，症状是"学过的词有时出现有时不出现"，极难排查。** 已写进 §8 的约束。

**③ RIME 从未承诺隐私与离线——这是我们能立的新旗帜**

三份报告一致确认：**RIME 的官方文档里找不到任何关于隐私、离线、数据本地化的承诺**（NOT FOUND）。相反，作者的开发计划第三期写的是：

> 「第三期，**添加網絡功能**，持續優化輸入效果；建立輸入法創作平臺。」—— `Introduction.md`

也就是说，**"离线 + 隐私"从来不是 RIME 的卖点，我们把它变成卖点，是一处真正的差异化**，而不是"我们也做到了 RIME 做到的"。

这直接影响 §0.1 的动机陈述：**我们的存在理由不只是"更小更快"，还包括"RIME 从未保证过的事"**。建议在 §0.1 里把这条提升为与内存/速度并列的第三根支柱。


### 13.4 一处**故意不同**：候选用全量排序，不用流式归并

RIME 把同一分段上多个翻译器的结果保存为 `Translation` 迭代器，靠 `Translation::Compare` **边取边归并**，只为效率（「爲了在有大量候選結果的情況下保持效率，Menu 僅在需要時……才會取得一定數目的候選結果」）。

**我们故意不这样做**（§4.1）：全量 + 限流 + 一次排序。

- **理由**：流式归并产生的是**局部有序**，跨翻译器的全局顺序依赖各自的比较策略；而我们需要**全序**才能满足"可复现"铁律（PLAN §5.2）。
- **代价**：全量排序在候选中等量级（≤200）下多花几十微秒，换来确定的、可测试的顺序。
- **结论**：这是一处**用微小性能换正确性**的有意偏离，不是疏忽。

### 13.5 方案切换的设计（D29）

RIME 作者把"**在会话中切换到不同的输入方式**"列为对 Engine 的两大期望之一。我们的实现：

```rust
/// 方案目录：应用级，持有**已装载**的方案，按内存预算惰性装载与淘汰。
pub trait SchemaCatalog: Send + Sync {
    /// 列出可用方案（只读元数据，不触发装载）。
    fn list(&self) -> &[SchemaInfo];

    /// 取用一个方案；未装载则装载；超预算则先淘汰最久未用的。
    /// 返回的句柄被丢弃时，该方案的注册被撤销（§6.3），内存随之释放。
    fn acquire(&self, schema_id: &str) -> Result<Arc<SchemaHandle>, SchemaError>;
}

impl dyn Session {
    /// 会话内切换方案。**失败时必须保持原方案可用**（§5.6：绝不让用户打不了字）。
    fn switch_schema(&mut self, schema_id: &str) -> Result<(), SchemaError>;
}
```

**四条约束**

1. **懒装载**：只装载用到的方案，不预载全部。
2. **内存预算 + LRU 淘汰**：预算是方案配置项（默认例如"最多常驻 2 个方案"或"最多 N MB"），**淘汰必须真的释放**（靠 §6.3 的注册回卷 / `Drop`）。
3. **切换失败要回退**：目标方案坏掉时，留在原方案并报诊断（D26）。
4. **用户词库跨方案共享**：RIME 的一份方案族（全拼/双拼）**共享同一个用户词典，并以全拼形式记录**。这是一个很好的设计——用户换双拼，学过的词不丢。**照抄这条。**

### 14.3 公开类型的兼容性约定（新增）

`stele-core` 的公开枚举一律标注 `#[non_exhaustive]`，理由：**引擎在 P1–P8 之间必然要加变体**（`Origin` 可能加"预测"、`Lane` 可能加第三条通道、`Trigger` 可能加语音上屏），而每个下游 `match` 都写死穷举会让每次加变体都变成破坏性变更。

```rust
#[non_exhaustive]
#[derive(Clone, Copy, PartialEq, Eq, Debug, PartialOrd, Ord)]
pub enum Origin { UserWord, SystemWord, Literal, Sentence }
```

**代价**：下游 `match` 必须写 `_ =>` 分支（多一行）。**收益**：内核演进不必每次发大版本。

**这是"内部项目也值得做"的一处**：我们自己的前端（`stele-cli`、TSF、Android）也是下游，不这么写的话，每加一个变体就要同时改三个前端。
