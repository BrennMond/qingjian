## 0. 问题（审计实测，不是推断）

同一个 release 构建、同一台机器、真实默认词库：

| 输入 | 结果 | 说明 |
| --- | --- | --- |
| `nihao` | 你好 | 正常 |
| `niha` | 只有字面量 | **不完整输入**完全失败 |
| `haoni` | 只有字面量 | 词表里没有「好你」，但有「好」「你」⇒ **不会造句** |
| `nihaoshijie` | 只有字面量 | 词表只覆盖前缀时**不会给前缀候选** |
| `ssss` 第 4 键 | 1.52 s / 209 MiB | 搜索资源上界不成立 |

第一行说明"整串查表"这条路是通的；后四行说明**这条路的形状本身不够**。
根因不是某个 bug，而是三个结构性缺口：

1. **拼写展开只产出"恰好消费完整个输入"的路径**，没有前缀消费；
2. **展开发生在词库查询之前、且不受词库约束**，于是大量不可能命中词库的
   路径先花掉 CPU 和内存（`ssss` 的 209 MiB 就是这么来的）；
3. **没有词图**（词与词之间的组合），所以"好"+"你"拼不出"好你"。

## 1. 分层与职责

```
输入串（用户敲的字节）
   │
   ├─(1) 识别器 / 分段器            recognizer → segmentor      ← 已有
   │
   ├─(2) 拼写图 SpellingGraph       音节边 + 输入跨度 + 属性     ← 待实现
   │        └─ 词典约束：只保留"可能是某个编码前缀"的路径
   │
   ├─(3) 词图 WordGraph             词条边 + 输入跨度 + 消费范围   ← 待实现
   │        └─ 有界动态规划造句（无语言模型）
   │
   └─(4) 候选                       文本 + 消费范围 + 余码 + 排序键
```

### 与现状的差别

| 层 | 现在 | 目标 |
| --- | --- | --- |
| (2) | `SpellingTable::expand_into` 返回 `Vec<CodeUnitId>`，只收"到末尾"的路径 | 返回**图**：节点带输入跨度，边带可信度/属性；允许部分消费 |
| 约束 | 无（先展开、后查词） | 展开时就用词库**前缀存在性**剪枝 |
| (3) | 不存在 | 词图 + 有界 DP |
| (4) | `Candidate.span` 恒为 `(0, code.len())`，无余码概念 | 真实跨度 + 余码 |

## 2. 拼写图（SpellingGraph）

### 2.1 形状

```text
节点 = 输入里的一个**字节位置**（0 ..= len）
边   = (from, to, spelling_text, code_unit_id, cost, attr)
```

一个输入串的拼写图是**预先编译好的拼写表**在该串上的投影：
从位置 0 出发，对每个位置找所有能匹配上的边。

- 边来自 `SpellingTable`（已实现，编译期产物，按键路径零分配）；
- 图本身在每次 compose 时按当前输入构建，节点数上界 = 输入长度 + 1。

### 2.2 输入跨度与部分消费

**这是与现在的根本差别。** 现在只有"到 `len` 才算一条路径"；
图模型里"到 `k < len` 的路径"同样有意义：

- 它给出**可解释前缀**（`niha` ⇒ `ni`+`ha`，还剩 `a`）；
- 它让**拼写层补全**有落脚点（剩余尾巴在拼写层展开，而不是要求它
  恰好构成完整编码）；
- 它让"未消费余码"成为一个**显式字段**，而不是被丢弃。

### 2.3 拼写层补全（`enable_completion`）

上游 librime：`TranslatorOptions::enable_completion_` 默认 `true`；
当 `Prism::ExpandSearch` 没覆盖到输入末尾时，补全发生在**拼写层**
（把尾巴当作前缀继续展开），不是"词库前缀查询"。

现在的实现把补全做成了 `lexicon.prefix_lookup(&exp.code, ...)`，
于是"尾巴构不成完整编码"时**根本到不了补全那一步**——`niha` 四格全败
就是这个原因（`reference/rime-sentence-and-completion.md` 的 2×2 矩阵）。

设计上分两种补全，**名字必须区分开**：

| 名称 | 在哪一层 | 语义 |
| --- | --- | --- |
| **拼写层补全**（`spelling_completion`） | 拼写图 | 未消费的尾巴作为前缀继续展开，产出"更长编码"的**音节路径** |
| **词条补全**（`word_completion`） | 词库 | 编码等于某前缀的词条（现有 `prefix_lookup`） |

`default_completion()` 当前返回 `false`，注释称"Rime 默认也是关闭"——
**那句注释是错的**，上游默认是 `true`。阶段 2 必须二选一：
与上游对齐（默认 `true`），或明确写成"Qingjian 有意不同"并给出理由与文档。

### 2.4 词典约束搜索（**这是 `ssss` 的根治手段**）

现在的搜索顺序是：**先**把所有拼写切分展开（受 `max_states`/`max_work`
硬限），**再**逐条查词库。绝大多数展开从一开始就不可能命中任何词条。

改法：给展开加一个**编码存在性预言机**：

```rust
/// 词库能回答的、与"是否存在"有关的问题。
pub trait CodeOracle {
    /// 存在以 `code` 为**前缀**的词库编码吗（含恰好相等）？
    fn has_prefix(&self, code: &[CodeUnitId]) -> bool;
    /// 存在**恰好**等于 `code` 的词库编码吗？
    fn has_exact(&self, code: &[CodeUnitId]) -> bool;
}
```

搜索只在 `has_prefix` 为真的节点上继续；到达末尾时再要求 `has_exact`
（或允许部分消费 + 造句，见 §3）。

- `InMemoryLexicon`：`BTreeMap` 的 `range` 天然给出前缀区间（O(log n + k)）。
- `TableLexicon`：编码段是**有序且连续**的，前缀区间 = 二分下界 + 顺序扫描，
  这正是审计 G4 要求补的 capability（阶段 3 第 2 项）。
- 词库不支持前缀查询时：**不能静默退化**。要么装载期拒绝开启补全的方案，
  要么在 `--dump-config` 里如实标注"该词库不支持补全"。

**约束搜索为什么不会漏召回**：一条不可能是任何词条前缀的路径，展开它
对最终候选没有任何贡献。约束是**语义等价**的剪枝，不是启发式近似——
这一点可以在测试里对着"无约束搜索的结果 ∩ 查得到的词"断言。

**代价**：`has_prefix` 落在按键路径上，每次展开一步一次。因此它必须是
O(log n) 的索引查询，不是扫描；`TableLexicon` 的实现必须走紧凑索引
（两台词库都已实现，见 `crates/qingjian-table/src/lexicon.rs` 与
`crates/qingjian-engine/src/lexicon.rs`，并有
`tests/lexicon_capability.rs` 守着两者语义一致）。

#### ⚠️ 一次**实测否决**的落地方式（2026-09，必须留着这条记录）

第一版把它接在了 `walk` 的**每一次边尝试**上：对每条候选边，用父指针
重建"父路径 + 这条边"的编码（复用同一个 scratch，不分配），再问一次
`has_prefix`，不通过就不入堆。逻辑是对的，**但实测是净亏**：

| 输入 | 未剪枝 P50 | 每次边尝试剪枝 P50 | 变化 |
| --- | --- | --- | --- |
| `nihao` | 109.9 µs | 97.2 µs | 略好 |
| `nhao` | 449.2 µs | 548.9 µs | **+22%** |
| `nh` | 238.1 µs | 308.9 µs | **+30%** |
| `ssss` | 493.9 µs | **1260 µs** | **+155%** |

（同一台机器、同一个 release 构建、真实默认词库、缓存命中。）

**为什么亏**：预言机的调用次数是"边尝试数"，而 `ssss` 的边尝试数是
3 万量级；而它的**剪枝收益**只在分支真的死掉时才兑现——`ssss` 的
s 音节在词库里存在（`沙士`/`上述`/`尚书`…），绝大多数分支**没有死**，
于是只付了成本、没拿到收益。`ni` 系输入同理：`n`/`n` 开头的编码在
41 万词条里几乎总有前缀，剪不掉。

**真正的正解**（下一阶段第一项，不是"再调一次参数"）：
**让 arena 节点自带"我的编码还是不是某个词条的前缀"这个状态**，
于是剪枝是**入堆时一次判断**（O(1) 的字段读），而不是每次边尝试一次
`O(depth)` 重建 + 一次二分。做到那一步需要把"前缀状态"做成搜索图上的
一等公民——例如在构建拼写图时就把词典的编码前缀树（trie）按需展开成
节点，而不是让"路径"与"词典"在搜索之后才相遇。

在那之前，**当前的行为是正确的**（有硬预算、有硬上界、召回完整），
只是没有拿到理论上该有的那部分性能。这条记录存在的意义是：
**下一个做这件事的人不必再走一遍这条弯路，也不该把"接了 has_prefix"
当成"实现了词典约束搜索"。**

### 2.5 资源合同（**已实现一部分**）

阶段 1 已经落地的部分（`crates/qingjian-engine/src/spelling.rs`）：

| 项 | 值 | 证据 |
| --- | --- | --- |
| `max_results` | 512 | `ExpansionLimits::default` |
| `max_units` | 16 | 同上 |
| `max_states` | 16384 | 实测反推，见常量文档 |
| `max_work` | 131072 | 同上 |
| 超限行为 | 停止探索、置 `truncated`、返回已找到的最优结果 | `ExpansionStats` |

**已实现**：中间状态是定长 24 字节的 arena 节点（父指针），不再每条
状态克隆一份 `Vec<CodeUnitId>`；`ssss` 的搜索图从 209 MiB 降到 <1 MiB；
release 下单键展开 <10 ms 有测试守着。

**待实现（阶段 2）**：`CodeOracle` 剪枝。它会把 `ssss` 的搜索图再降一个
数量级，并让 `nhao` 这类"贵切分"不再依赖预算的大小——
因为不可能命中词库的分支根本不会被展开。

## 3. 词图与造句（WordGraph / Poet）

### 3.1 词图边

```text
词图边 = (input_from, input_to, text, code, score, origin, attr)
```

- `input_from..input_to`：这条词**消费了输入的哪一段**（字节）；
- 一条拼写图路径到达位置 `k` 时，词库给出所有"编码 == 该路径"的词条，
  每条成为一条词图边；
- 同时允许**单字**作为边（这正是"造句"的原子）。

### 3.2 有界动态规划

没有语言模型时，`Poet` 的做法是动态规划：在词图的所有"覆盖输入"的
路径里选分数最好的。我们的设计：

```
best[0] = 0
best[j] = max over edges (i → j) of ( best[i] + edge.score - LENGTH_PENALTY )
```

- **上界**：词图边数 ≤ `max_word_edges`（建议 4096），`best` 长度 = 输入长度 + 1；
- **必须防的两件事**（审计点名）：
  1. **单个整词候选与组合候选重复**——同一条输入既可能是"整词"，也可能是
     "词 + 词"。两边都要给出，但**去重键是（消费范围, 文本）**，
     并且整词候选必须排在它所分解出的组合之前（同分时按边数升序）。
  2. **无限组合 / 过度候选**——DP 天然不会无限；"过度候选"由
     `max_word_edges` 与最终的 `candidate_cap` 双重限流。
- **确定性**：DP 的平局键固定为 `(score desc, 边数 asc, 文本 asc, 消费起点 asc)`，
  与现有 `sort_candidates` 的确定性要求一致。

### 3.3 词库接口

**不允许**"把 41 万词条全扫一遍来造句"。词图只需要
"**从位置 `i` 开始的、编码等于某条拼写路径的那些词条**"——
这正是拼写图 + 词典约束搜索已经给出的东西。造句不新增扫描，
它只是在**已经查出来的词条**之间做组合。

这一条是设计上的硬约束：如果某个造句实现需要遍历整个词库，
那它就是错的实现。

## 4. 候选的消费范围与余码

### 4.1 类型层

现在 `Candidate.span` 是"编码单元下标区间"，而在**拼写图**语义下
真正需要表达的是**输入字节区间**：

```rust
pub struct Candidate {
    /// 这条候选**消费了输入的哪一段**（字节）。
    pub consumed: Span,
    /// 没有被消费的余码（`input[consumed.end..]`）。
    /// 空 = 恰好消费完。
    pub remainder: String,
    ...
}
```

**不这样做会怎样**：`niha` 的前缀候选必须"消费 `niha` 里的 `ni`+`ha`
并把 `a` 留在预编辑里"。现在的 `finish_commit()` 一次清空整个
composition，根本无法表达"这段确认了、剩下的接着打"。

### 4.2 与现有 trait 的迁移

| 现有 | 迁移 |
| --- | --- |
| `Candidate.span: Span`（编码单元区间） | 保留（用于词库截断与去重），**新增** `consumed`/`remainder` |
| `Spelling::expand(&str, &mut ExpansionSink)` | **新增** `expand_graph(&str, &CodeOracle, &mut GraphSink)`；旧方法保留为"无约束、到末尾"的兼容入口 |
| `Lexicon::prefix_lookup` | 保留；**新增** `has_prefix`/`has_exact`（`CodeOracle` 的实现来源） |
| `Translator::translate` | 不改签名；内部改为走图 |

**迁移原则**：先加新入口、让旧入口变成"新入口的一个退化调用"，
再逐个翻译器切换。这样每一步都有可回退点，也保证现有测试全程为绿。

## 5. 复杂度与内存预算

记 `L` = 输入字节长度，`E` = 拼写表边数（装 399 音节 + 缩写 ≈ 800），
`W` = 词库查询返回的词条数上界。

| 阶段 | 时间 | 空间 |
| --- | --- | --- |
| 拼写图构建 | O(L · α)，α = 每个位置的平均匹配边数（≤ 音节表首字母分组大小） | O(L) |
| 词典约束搜索 | O(min(max_states, 命中前缀的状态数) · 单步查询) | O(max_states) |
| 词图边 | O(路径数 · W)，受 `max_word_edges` 截断 | O(max_word_edges) |
| DP 造句 | O(max_word_edges · L) | O(L) |

- `max_states = 16384`、`max_work = 131072`、`max_results = 512`、
  `max_word_edges = 4096`（建议值，实现时实测反推）；
- 全部是**与输入长度无关的常数上界**——这是"按键路径有确定资源上界"
  这句话的具体含义；
- 超限时的行为：置 `truncated`、返回已有最优结果。**不 panic、不静默改语义**。
  可显示的降级：前端可以据此提示"输入过长，已截断"。

## 7. 明确不做的事

- **不把 `max_expansions` 调大**来"解决"召回问题——那是把资源问题换成
  资源问题（审计 §2.A 明令禁止）；
- **不把输入直接退化成字面量**来让预算好过——测试同时断言目标候选召回；
- **不引入神经语言模型**作为造句的前提：第一版只用语词频与长度策略；
- **不声称与 Rime 完全一致**：`script_translator` 与 `table_translator`
  对 `enable_sentence` 的归属本就不同，Qingjian 可以有自己的语义，
  但必须**文档化**并且不谎称相同。
