# 青简近期收敛方案：Windows 电脑自用优先

> 给后续执行者（DeepSeek）的执行基线。
>
> 本文是项目范围收敛说明，不要求两天内做出成熟输入法，也不把青简改成
> librime 的 Rust 逐行重写。

## 1. 项目定位

青简是一个**独立的 Rust 输入法项目**：借鉴 Rime 的方案化、组件化、拼写层与词典层分离等设计思想，并选择性参考 Rime 的输入行为；它不是 librime 的直接移植，也不以加载全部 Rime schema 为目标。

因此：

- Rime / rime-ice 是设计与行为参考，不是必须照搬的产品规格；
- 不承诺现成 Rime 方案无需修改即可运行；
- “不能直接加载 Rime 方案”是兼容性边界，不是青简内核失败；
- 不得把“参考 Rime”写成“完整兼容 Rime”或“完全重写 librime”。

## 2. 当前真实目标

项目初衷是作者自己使用，而不是现在就完成通用、成熟、跨平台输入法平台。

近期目标收敛为：

> **Windows 电脑 + 全键盘拼音 + 一个固定的自用方案和词库 + 最薄可用的 TSF 前端。**

验收终点不是“实现 Rime 的全部能力”，而是作者可以在自己的 Windows 电脑上进行真实日常输入，并且遇到问题时仍能切回现有输入法。

## 3. 近期明确不做

在 Windows 自用闭环前，冻结以下方向：

- Android 前端；
- 手机九键输入及其专用方案；
- 全量 Rime schema / preset 兼容；
- 更多输入法方案；
- 向量重排的继续扩展；
- 为了终局设计而提前重写 Pike VM、词典前缀状态搜索等非阻塞算法；
- 设置中心、主题、同步、词库市场等产品外围。

手机输入法，尤其九键，是独立的产品和技术路线：按键歧义、触摸候选、生命周期、密码框、内存预算和专用方案都不能从桌面全键盘自然推出。以后另立阶段，不作为当前 Windows 目标的隐含要求。

## 4. Windows 第一版最小闭环

只实现能让作者实际使用的最小 TSF 路径：

1. 注册一个 Windows TSF Text Service；
2. 接收键盘事件并交给 `Session::process_key()`；
3. 显示最小预编辑文本；
4. 显示基本候选窗；
5. 支持空格、数字选择和必要的翻页；
6. 把 `Commit` 插入当前应用；
7. 中英切换、退格、取消、基本标点能工作；
8. 密码框、不可编辑控件和异常上下文不抢输入、不学习；
9. 前端出错时可退出并切回系统/现有输入法。

第一版不追求完整候选窗视觉效果，也不要求完整 Rime 会话语义；但不得静默丢输入、错误提交或损坏用户记忆。

## 5. 内核执行原则

- 先冻结现有内核接口和外围功能，避免继续扩大架构；
- 只修真实使用阻塞项：错词、错选、丢字、卡顿、崩溃、前端契约不清；
- 现有资源硬上界和可靠性保护必须保留；
- 自动机正则、arena 前缀状态搜索、全量词级读音等是后续技术改进，不是 Windows 自用第一版的自动阻塞项；
- 对于 Rime 行为，只有在青简确实选择复现时才做 oracle 对照；不为“兼容全部 Rime”无限扩张范围。

## 6. 给执行者的工作顺序

1. 阅读本文件、`PLAN.md`、`docs/HANDOFF.md`；
2. 不新增 Android、九键、全量 Rime 兼容任务；
3. 明确当前 Windows TSF 与 `Session` 的最小桥接契约；
4. 先做最薄的前端可运行验证，不先做设置界面；
5. 用作者自己的日常输入集验收；
6. 记录真实阻塞问题，再按影响排序修复；
7. 每次修改都保持 CLI、内核测试和现有安全/资源门禁通过。

## 7. 当前状态的诚实表述

青简已经是可运行、可测试、可扩展的 Rust 输入法**原型内核**，可以进入 Windows 前端实验；它还不是成熟日用输入法，也不是 Rime 的 drop-in replacement。目标是逐步让作者自己用起来，而不是先完成一个“所有人、所有平台、所有方案”的终局系统。
