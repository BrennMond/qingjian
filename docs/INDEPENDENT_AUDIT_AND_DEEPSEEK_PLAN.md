## 0. 执行摘要

### 0.1 总结判断

Stele **不是空壳**。它已经有：Rust 分层、两类翻译器、方案装载、拼写规则、紧凑词库、候选排序、可选本地记忆、CLI、相当多的回归测试和若干可重跑的 Rime 对照工装。核心 crate 禁止 `unsafe`、保持零第三方依赖，以及把方案与内核分开的方向，也都有工程价值。

不过它仍是**原型内核**，距离“可以承载接近商业拼音体验的输入法”有关键距离。问题不在少一个 Android UI，而在下面四类内核事实：

1. **核心解码模型不足**：当前主要是“整串输入 → 完整展开路径 → 查词”；缺少 Rime 拼音路径中决定日常体验的前缀消费、拼写层补全、词图和动态造句。
2. **资源上界不成立**：短词基准很快，但某些常规/病态短输入能在按键路径造成秒级延迟和数百 MiB 临时峰值。不能用 `nihao` 的 P50 代表全部打字性能。
3. **有明确正确性与可靠性错误**：缓存未绑定字母表映射、损坏二进制词库会触发 panic、用户记忆写失败会错误清除 dirty 状态。
4. **“兼容 Rime 配置”尚为有限子集**：13 个本机可用的上游 preset 方案均不能直接装载；一些同名字段被解析但没有运行时效果，或语义与上游不同。

**总策略：不要推倒重写；不要继续优先叠加向量记忆、预测、计算器等外围能力。先修可靠性和复杂度上界，再重构解码/会话主路径，然后扩展默认词库与配置兼容性。**

### 0.2 不可接受的宣传口径

在整改完成前，README、PLAN、HANDOFF 和对外材料不得声称或暗示：

- “已可替代成熟日常中文输入法”或“接近搜狗体验”；
- “真实按键路径零磁盘 I/O”（当前真实 `TableLexicon` 查询使用 `read_at`；只有用户记忆热路径的零 I/O 被专门测试）；
- “常驻 <30 MB / P99 <10 ms 已普遍达标”（当前只对特定短输入、特定环境有证据）；
- “Rime 因为旧、依赖多、没有把隐私写进设计文档，所以不现代或不隐私”；
- “仓库不包含第三方词典数据”（已跟踪的生成词库是第三方 MIT/Apache 来源的派生产物）；
- “完全/直接兼容 Rime 方案”。

这些不是要求贬低项目，而是要求把**已测事实、目标、推断和未验证假设分开**。

## 2. 问题清单、证据、优先级与整改要求

优先级定义：

- **P0 / 阻断**：会静默错误、丢失用户数据、崩溃，或使输入路径无确定资源上界。不得进入任何前端集成阶段。
- **P1 / 高**：日常核心能力缺失或配置声明与实际行为严重不一致。不得宣称接近成熟拼音输入体验。
- **P2 / 中**：实验词库质量、兼容性、可维护性或产品边界问题。可并行推进，但不能用来取代 P0/P1。

### A. P0：拼写展开搜索存在按键路径资源爆炸

**位置**：`crates/stele-engine/src/spelling.rs`，`SpellingTable::expand_into`，尤其是状态 `(pos, Vec<CodeUnitId>)`、`BinaryHeap`、`HashSet` 和路径 clone。

**已复现事实**：

- `ssss` 的第四次按键约 1.52 秒，过程峰值约 209 MiB；最终仍只是字面量 `ssss`。
- `woaizhongguo` 输入过程出现百毫秒级按键，峰值约 146 MiB，最后也退化为字面量。
- 当前预算限制出队数量、单位数量和完成结果数量，但没有以“中间状态数 / 路径字节数 / 单键耗时”形成真正资源上界。
- 词典查询仍发生在路径展开之后；大量不会命中词典的路径已消耗内存和 CPU。

**为何严重**：输入法位于每一个按键的同步路径。数百毫秒乃至秒级卡顿会直接影响应用；数百 MiB 瞬时分配也与轻量目标相冲突。

**DeepSeek 必须完成：**

1. 建立 `spelling_resource_bounds` 回归测试：至少覆盖 `ssss`、`woaizhongguo`、高歧义简拼和较长合法输入；测试必须测量或注入可观测的：探索状态数、路径/堆上界、查询数和耗时预算。
2. 先交设计说明，再改实现。设计必须说明：状态表示、去重键、词典约束何时介入、候选截断的语义、输入长度策略、取消/降级策略。
3. 推荐方向是**共享音节/拼写图 + 词典约束搜索 + 词图解码**，而不是继续复制整条 `Vec<CodeUnitId>` 路径、或把 `max_expansions` 从 512 调得更大。
4. 明确全局资源合同，例如每次 compose 的最大状态数、最大临时字节、最大查询数、最长输入行为；超限时要有确定、可测试、可显示的降级，而非 panic 或无界卡顿。
5. 在真实词库和合成高歧义词表上跑基准；报告 P50/P95/P99/最大值及峰值内存，不能只报告 `nihao`。

**验收最低线：**

- 现有复现输入在 release 下不再出现 >10 ms 的单键路径（需要在受控基准环境中设门槛；CI 可用状态数/分配上界替代绝对时间）。
- 测试能证明中间状态受硬上限控制，且正常词不会因该上限静默丢失。
- 不能为了通过测试而将输入直接退化成字面量；应同时断言目标候选召回。

### B. P0：部署词库缓存没有绑定字母表映射，会静默错码

**位置**：`crates/stele-schemes/src/file.rs:1527` 附近，`deploy_dict`；`CodeAlphabet` 将列表下标作为 `CodeUnitId`。

**最小复现：**

```yaml
# 初始
speller:
  alphabet: [ni, hao]
# 词典：你 ni；好 hao
```

首次部署后输入 `ni` 得到“你”。只把 `alphabet` 改为 `[hao, ni]`，不改词典，缓存仍被复用；输入 `ni` 得到“好”。删除 `.stele-cache` 后重新编译才恢复“你”。无诊断。

**根因**：二进制表保存了编号，缓存键只依赖词典原始内容；编号到编码单元文本的映射没有进入缓存身份。

**DeepSeek 必须完成：**

1. 缓存身份加入所有影响产物语义的内容：至少格式版本、字母表内容及顺序、词典及 import 链原始字节、编译选项；推荐定义一个明确的 `BuildFingerprint`，固定编码而非临时字符串拼接。
2. 缓存文件名或头部必须包含/验证 fingerprint；旧缓存需失效或能明确迁移。
3. 添加上述“仅重排 alphabet”的端到端测试：不清缓存、重新装载、仍必须正确得到“你”；并断言确实重新编译或选用新缓存。
4. 评估多个 translator/词库实例时的 fingerprint 隔离，避免名称冲突。

**验收最低线：** 修改任一语义输入后，绝不可复用会产生不同码元映射的旧产物；必须拒绝或重建。

### C. P0：损坏 `.table` 的内部索引可使 release 进程 panic

**位置**：`crates/stele-table/src/lexicon.rs`，`TableLexicon::open_checked` 与 `find_code`。

**已复现事实**：只篡改缓存二进制的一个内部 `unit_offsets` 值，保持文件总长度、魔数、格式版本和 source checksum 不变，装载成功；查询时在切片范围处 panic：

```text
range start index 10000 out of range for slice of length 2
```

source checksum 仅表明源词典内容，**不是产物完整性校验**。

**DeepSeek 必须完成：**

1. 在 `open_checked` 做完整结构验证，且任何来自文件的 offset/length 在切片前都经过 checked arithmetic 和范围验证。
2. 至少验证：各 offsets 单调；第一个/最后一个哨兵正确；`unit_offsets` 不超过 `total_units`；`entry_offsets` 不超过 `entry_count`；区段不重叠；entries 和 words 区域均位于 file size 内；所有乘法/加法不溢出。
3. 增加产物完整性校验。可用校验和覆盖产物主体，或通过可靠的原子发布/重建机制保证缓存不可见半成品；须说明威胁模型。FNV 只能防意外损坏，不是安全防篡改，文档不能称其为安全边界。
4. 所有损坏样本必须返回 `FormatError`/重新部署诊断，绝不能 panic 或 `process::abort`。
5. 可考虑模糊测试 / cargo-fuzz 或无依赖随机畸形输入测试；至少覆盖 header、所有 offset 数组、entry 区、word 区的截断、翻转和溢出。

**验收最低线：** 使用畸形缓存运行 CLI，结果只能是安全拒绝、重建或可读错误；不得崩溃。

### D. P0：用户记忆写盘失败后会丢失重试机会

**位置**：`crates/stele-memory/src/store.rs:464–515`，`FileMemory::flush`。

**已复现事实**：当前在写临时文件之前即把 `inner.dirty = false`。故障注入（将 `<userdb>.tmp` 预先建为目录）后：

```text
flush() -> Err(IsADirectory)
dirty == false
移除障碍后再次 flush() -> Ok(false)
目标文件不存在，内存中的记录未被保存
```

**DeepSeek 必须完成：**

1. 只有在临时文件完整写入、同步策略完成、`rename` 成功后，才清 `dirty`；发生任意错误必须保留 dirty，以允许显式重试。
2. 检查锁的粒度：不能因持锁 I/O 阻塞热路径；也不能在 clone snapshot 与清 dirty 之间丢掉并发新写入。必要时使用代次/version counter：仅当成功保存的快照仍是当前代次时才清 dirty。
3. 临时文件不能固定为 `<name>.tmp`：使用同目录唯一文件名（随机或安全计数），并处理残留临时文件；考虑多进程竞争。
4. 实现多实例/多进程策略：文件锁、版本比较+合并、单 writer 服务，三者至少选择一种并有明确文档。当前两个 `FileMemory` 句柄依次保存，后写者会覆盖先写者的数据，已复现。
5. 恢复时必须施加 `cap` / `predict_cap`，当前“cap=1 重开含 10 条文件”仍加载 10 条。明确保留策略并测试。
6. Android 前端尚未开发，但现在就定义生命周期合同：何时 debounce 保存、何时 onStop/onTrimMemory 保存、失败如何提示/重试；不要仅依赖正常进程退出。
7. 在 Unix 上将新建记忆文件显式设为所有者可读写（通常 `0600`），并在 Android 使用 app-private storage。权限不是完整隐私方案，但应避免默认扩大可读范围。

**验收最低线：** 写盘失败后仍 `dirty`、可重试；并发更新不静默覆盖；坏文件不覆盖；容量上限在加载后也成立。

### E. P1：拼音核心缺少前缀消费、拼写层补全与词图造句

**上游事实（librime 源码和实际 1.16.1 探针共同支持）：**

- `src/rime/algo/syllabifier.cc` 维护 `input_length` 与 `interpreted_length`；后者可小于完整输入，因此可以只解释可识别前缀。
- 当启用补全且未覆盖到输入末尾时，`Prism::ExpandSearch` 在**拼写层**补尾巴；librime `TranslatorOptions::enable_completion_` 默认是 `true`。
- `ScriptTranslation` 在音节图的各位置查词，形成 `WordGraph`；没有可靠整词时可调用 `Poet::MakeSentence`。无语言模型时走动态规划，并非必须接神经模型。

**同词表对照复现：**

| 输入 | librime | Stele 当前 |
|---|---|---|
| `nihao` | 你好 | 你好 |
| `niha` | 你好等 | 仅字面量 `niha` |
| `haoni`（词表中无“好你”，有“好”“你”） | 可造句“好你” | 仅字面量 |
| `nihaoshijie`（词表只覆盖前缀） | 给可解释前缀候选 | 仅字面量 |

`reference/rime-sentence-and-completion.md` 的 2×2 “缩写 × 补全”矩阵进一步确认：Stele 对不完整 `niha` 四格都失败；并非只差一个开关。

**当前代码问题：**

- `SpellingTable::expand_into` 只产出到达整串末尾的路径；
- `SpellingGraphTranslator` 的补全是 `lexicon.prefix_lookup(&exp.code, ...)`，因此当前尾巴不能形成完整编码时根本到不了补全；
- `TranslatorSpec::enable_sentence` 被读取但没有真正消费；
- `default_completion()` 返回 `false`，注释称 Rime 默认也是关闭，但上游默认 `true`；
- 目前没有对应 `WordGraph` / `Poet` 的结构。

**DeepSeek 必须完成：**

1. 在修改前写 `docs/decoder-design.md`：定义音节图边、输入跨度、可信度/拼写属性、词图边、候选消费范围、未消费余码、排序、复杂度和内存预算。
2. 将“拼写分析”结果从仅 `Vec<CodeUnitId>` 路径，提升为能表示输入位置区间和属性的共享图。不可把每条完整路径复制后再查表作为主算法。
3. 在拼写图上支持：
   - 可解释前缀；
   - 拼写层补全；
   - 编码/词条补全（若保留）；
   - 完整输入、未消费输入的明确候选范围。
4. 词典需要提供适合图查询的接口；不要把 41 万条词表全扫描来“造句”。
5. 实现有界的词图动态规划。第一版可以不接语言模型：以词频和长度策略组合词条；必须防止单个整词候选与组合候选重复、无限组合和过度候选。
6. `enable_sentence` 必须按清晰的方案语义实现或明确拒绝；不要继续“解析但静默不生效”。注意上游 `script_translator` 与 `table_translator` 对该字段的归属并不完全相同，Stele 可设计自己的语义，但需文档化且避免伪称相同。
7. 补全默认值要么与 Rime 对齐，要么明确是 Stele 有意不同；不得保留错误的上游注释。

**验收最低线：** 上表四例及缩写×补全矩阵纳入硬性测试；实现必须同时检查候选文本、消费范围/余码和属性，而非只断言“有某个候选”。

### F. P1：会话分段、选择、余码和标点语义尚未闭环

**观察**：当前 `SessionImpl` 的选词最终走 `finish_commit()`，清空整个 composition。成熟输入法需要逐段确认、候选覆盖特定 span、余码继续存在、可重新开启已选段。现有 `Confirmed` / `Reopen` 等接口或注释不能算作行为已经实现。

对比探针：librime 输入 `ni,` 会提交“你，”；当前默认 Stele 路径中逗号返回 `Rejected`，`ni` 仍留在预编辑中。这未必是“代码 bug”——当前标点处理器文档已明确选择了另一种交互——但它是与 Rime 不同、且会影响前端设计的**产品语义差异**，需要明确决定并测试。

**DeepSeek 必须完成：**

1. 定义一套会话状态机：输入、猜测段、已确认段、选词、重开、光标位置、余码、取消、标点插入、英文/数字段。
2. 在 `Session`/`Composition` 类型层表达候选覆盖的 span 和提交后的剩余输入；不可通过“选中后总清空”掩盖复杂度。
3. 为以下交互写端到端状态转换表和测试：
   - 部分选词后继续输入；
   - 选择第二段；
   - Backspace / Delete / Esc；
   - 重新选择已确认段；
   - 输入中插标点；
   - 全半角、中英切换、数字和 URL/特殊识别器；
   - 预测候选与数字选择的隔离。
4. 先决定是否严格对齐 Rime；若有意不同，更新注释和用户文档，保留对照测试说明。

### G. P1：方案装载与运行语义存在实证缺口

#### G1. 上游方案装载：13 个样本均失败

本机 `/usr/share/rime-data` 的 13 个方案逐个隔离装载，结果为 0 成功。主要缺口：

1. Rime 字典 `columns:`、`%` 百分比权重和非数值列；
2. 码表方案的无空格字符串编码；
3. 跨文件 `__patch` / `__include` 语义；
4. Rime 的单选组 `options:`；
5. 部分 X11 keysym 名称；
6. Rime preset 资产（`default` / `symbols`）未提供。

这不是要求 Stele 必须兼容所有 Rime 配置；而是要求对外把能力称为**“Rime 风格的受限子集”**，直到每个支持项有端到端证据。一个坏方案目前还会中止整个目录加载；这与“配置错误不阻止启动”的目标也有冲突，需要设计产品级加载策略。

#### G2. `xlit` 语义不对

`spelling.rs` 的 `Rule::Xlit` 保留原拼写再追加转写结果，等价于派生；官方 wiki 和 librime `Transliteration::Apply` 表明 `xlit` 是改写。最小例：`xlit/a/b/` 与原编码 `aa`：librime 中 `bb` 有效、`aa` 无效，Stele 两者都有效。

**要求**：将 xlit 改为 transformation 语义；添加与上游的直接回归测试。不要以“用户也许希望保留原输入”改变同名 Rime 操作符；如需此功能，定义一个新的 Stele 专用操作符。

#### G3. 多 translator 实例的词库选择不正确

审计构造两个 `script_translator`，主词库含“甲”、`script_translator@other` 词库含“乙”，输入同码仅得到“甲”。装配路径持续使用 `self.lexicon`，并未按实例 `TranslatorSpec.dictionary` 选择词库。

**要求**：建立“每个实例独立词库”的资源图；翻译器实例、词典、拼写表、反查资源的关系必须明确。补 `script_translator@alias` / `table_translator@alias` 两类端到端测试。

#### G4. 内存词库和部署词库能力不一致

显式 `enable_completion: true` 时，小方案使用内存词库可从 `ni` 得到“你、你好”；走实际二进制部署词库只得到“你”。`TableLexicon` 没有相应 prefix 查询实现。

**要求**：同一 `Lexicon` trait 的能力必须在不同实现上有能力声明和同一语义测试。若二进制词库暂不支持前缀查询，装载时应拒绝/警告开启补全的方案，不得静默退化。优先实现紧凑索引的 prefix range 查询。

#### G5. 解析不等于生效

已发现或应系统排查的字段：`enable_sentence`、`initial_quality`、实例 dictionary、`reverse_lookup_filter` 的数据源、completion 等。

**要求**：建立配置字段审计表：

| 字段/组件 | 解析位置 | 装配位置 | 运行消费位置 | 端到端测试 | 不支持时的诊断 |
|---|---|---|---|---|---|

所有公开声称支持的字段均要填齐。`rust-analyzer` 的 references/call hierarchy 是检查“声明是否真被消费”的辅助工具，但最终必须由行为测试确认。

### H. P1：自写 regex 与 recognizer 有错误匹配及 ReDoS 型卡顿

**位置**：`crates/stele-engine/src/regex.rs`、`crates/stele-engine/src/segmentor.rs`。

#### H1. `leading_literal` 优化错误地拒绝合法模式

实测：

| 正则 | 输入 | Regex 本身 | Recognizer |
|---|---|---|---|
| `^(a|b)+$` | `bbb` | 匹配 | 未认领 |
| `^https?://.*$` | `http://x` | 匹配 | 未认领 |
| `^a?b$` | `b` | 匹配 | 未认领 |

根因是近似前缀提取把“某一分支/可选项的首字符”当作必需前缀。优化只能产生假阳性（多做一次完整匹配），不能产生假阴性（漏识别）。

**要求**：暂时移除 leading shortcut，或用保守语法分析证明“提取的字符串是全部匹配的共同必需前缀”；新增属性测试：任何输入，只要 `Regex` 匹配，启用/禁用优化后的 recognizer 结论必须一致。

#### H2. 递归回溯可指数爆炸

`^(a+)+$` 对 `a...ab`：20 个 `a` 约 54 ms，24 个约 848 ms，28 个在审计 3 秒超时。代码注释假定“只处理短音节”，但 recognizer 也使用同一实现，输入未必短。

**要求**：

1. 不要再以注释宣称不存在风险。
2. 最好改用保证线性/多项式时间的有限自动机实现或经审计的 regex 引擎；若零依赖是硬要求，需明确缩小支持语法，采用 NFA/DFA，并有复杂度证明/测试。
3. 若短期不能重写，至少有编译期规则拒绝危险嵌套重复，运行期有步骤/栈/输入长度预算，且超限以可诊断方式不匹配；这是临时缓解，不能当最终方案。
4. 禁止递归深度随输入无界增长；加压力测试和 fuzzing。

### I. P2：实验默认词库的词级读音不足

**范围说明**：默认词库已经被项目定位为实验性、自建且可替换。它目前的质量问题不意味着内核设计整体失败，但若目标是普通中文输入，必须成为高优先的产品工作流。

`tools/wordlist-gen` 主要根据单字 `pinyin.txt` 的首读音和有限同声母启发式给词编码；缺少词级读音。已核对的常见词：

| 词 | 当前编码 | 常见正确编码 |
|---|---|---|
| 银行 | `yin xing` | `yin hang` |
| 重庆 | `zhong qing` | `chong qing` |
| 音乐 | `yin le` | `yin yue` |
| 重新 | `zhong xin` | `chong xin` |

因此 `yinhang` / `chongqing` 不召回目标词，而错误读音会召回。词不存在正确编码时，任何排序、个人记忆和向量都无法修复。

**DeepSeek 必须完成：**

1. 不要把“先做词级读音”与 P0 算法/可靠性工作冲突；可并行设计，但不要让数据修补掩盖内核 bug。
2. 寻找并审查可分发的词级拼音来源；记录许可证、版权、版本、hash、转换脚本和合并规则。
3. 支持受审计的人工覆盖表，覆盖常见多音字、地名、人名；覆盖表也要有来源和测试。
4. 建立质量评测集，独立于生成器的训练/来源数据：常用词、地名、人名、多音字、简拼、混输。报告召回率、首选率、前五命中和错误类型。
5. 词典格式应允许一个词有多个读音和权重，不能在数据生成期永久只选一个读音。

### J. P2：隐私、存储与许可是产品前置设计，不是最后补文案

#### J1. 隐私边界

正面事实：当前查看的 Rust 运行路径未发现联网或遥测；用户记忆默认关闭；损坏记忆不会自动覆盖。这些都值得保留。

但用户记忆包含上屏文本、编码、上下文、频次与时间；它是敏感本地行为历史，虽非逐键日志。当前默认环境中记忆文件模式为 `0644`（实际可访问性还取决于父目录）。未来 Android 还需要处理密码框、私密应用、跨应用上下文、系统备份和日志。

**要求**：在前端设计前完成 `docs/privacy-model.md`，定义：不收集/不联网承诺、数据分类、磁盘位置与权限、敏感输入禁学、清除与导出、日志规则、第三方库/模型、Android 权限与备份。并实现 API，不是只有文档。

#### J2. 许可与可复现来源

仓库的 `generated.dict.yaml` 是已跟踪的大型派生词库；来源脚本列出 pinyin-data、THUOCL、jieba、OpenCC、rime-ice 的 OpenCC 资源等。工具目录还跟踪了从 rime-ice 复制/改写的 Lua oracle 文件。README 的“本仓库不包含第三方词典数据或模型”与事实不符。

已核对的 pinyin-data、THUOCL、jieba 上游 MIT 许可证要求保留版权和许可证文本。这里不作法律结论，但当前不能仅靠“来源是 MIT/Apache”完成分发审计。

**要求**：

1. 新建根目录 `THIRD_PARTY_NOTICES.md`（或合适标准文件），逐项列出：文件/生成物、上游 URL、固定 commit/tag、版权、许可证、是否修改、适用的随附许可证文本。
2. 将下载来源由浮动 `main/master` 改为固定 revision 或 release asset；将 SHA-256 清单作为已跟踪可复现输入，不要只存在 `.gitignore` 的构建目录。
3. 为所有直接复制、翻译或派生代码/数据重新核对许可；如不希望分发相关 Lua，移除其源码及生成说明，或依许可证正确保留声明。
4. 修改 README 的错误陈述，准确区分“未分发 rime-ice 大词库”与“分发了哪些第三方派生数据”。

## 3. 对 Rime 的公平比较

### 3.1 应当承认的 Rime 优势

librime 不是单纯“整串查表”的旧引擎。源码和 wiki 均表明它具备：模块化组件、方案 YAML、拼写代数、音节图、词图、动态造句、用户词典、不同前端以及长期方案生态。它本身是 BSD-3-Clause；特定词库/方案可能是其他许可，二者不可混同。

基础 `script_translator` 的造句不要求 Lua 或神经语言模型；无 grammar 时 `Poet` 仍走动态规划。重度 Lua 方案的性能不能代表 librime 基础内核。

Rime 官方文档没有写“隐私承诺”，以及 2009 年计划中出现“添加网络功能”，都**不能推导出当前 librime 必然联网、遥测或不保护隐私**。上游用户数据同步代码读取/合并本地同步目录中的快照；是否联网取决于具体前端、部署、插件和用户配置，需逐项审计。

### 3.2 Stele 可以建立的真实优势

- 更易审计的 Rust 内核；
- 小依赖面、无 `unsafe`；
- 方案和内核分离；
- 可选且默认关闭的本地记忆；
- 紧凑词表在简单负载下的低内存潜力；
- 更严格、更可读的配置诊断和测试文化。

但优势要建立在**正确、受界且可用的基础能力**之上。少做动态造句、部分输入和兼容功能后得到较低 RSS 或短词延迟，不构成整体胜出。

### 3.3 建议的对外定位（整改前）

> Stele 是受 Rime 思想启发的 Rust 输入法引擎研究/原型。当前提供实验性方案、词库和 CLI 验证环境；重点在可审计性、离线可选记忆和轻量化探索。尚未提供可替代完整桌面或手机输入法的前端产品，也尚未宣称完整兼容 Rime 生态。

## 5. 工具使用规范（供 DeepSeek）

### 5.1 Rust 侧静态与动态检查

每次提交前至少运行：

```bash
cargo fmt --all -- --check
cargo clippy --workspace --all-targets --offline --locked -- -D warnings
cargo test --workspace --offline --locked
for f in scripts/verify-*.sh; do bash "$f"; done
cargo run -p stele-cli -- --check
```

建议使用：

- `rust-analyzer` 的 Find References / Call Hierarchy：检查配置字段、组件、trait 方法是否真的有消费点；
- `cargo test -p <crate> <test> -- --nocapture`：先运行最小回归；
- `cargo llvm-cov`（若已安装）或其他覆盖工具：确认故障分支确实执行；
- Miri（若可用）：检查不安全假设以外的 Rust 逻辑/UB 边缘；
- proptest / libFuzzer / cargo-fuzz（根据依赖策略决定）：对二进制格式和正则进行畸形输入测试；
- `/usr/bin/time -v`、`/proc/self/status`、受控 benchmark：分别报告峰值和稳态，勿混用。

静态分析只能发现“字段无人读取”“可能 panic”等线索；它不能证明 IME 行为与 Rime 一致。端到端键序列测试仍是必需。

### 5.2 C++ / librime 取证规则

本机已有 `clangd` 和 `rg`。阅读上游时：

1. 固定 commit；报告中写路径和行号；
2. 使用 `rg` 找符号后，用 clangd 查调用点/类型关系；
3. 不要仅凭 wiki 或注释推断 C++ 实际行为；
4. 需要运行事实时用 `tools/librime-probe/`，明确它使用的是系统 librime 1.16.1；
5. 比较要保持词表、开关、词典和冷/热启动条件一致；
6. 无法验证的结论必须写“待验证”，不可伪装成上游事实。

### 5.3 现有工装的边界

- `tools/librime-probe/`：真实运行库探针；不是 master 编译物。
- `tools/rime-compare/compare.py`：A/B1/B2 是硬断言；B3/B3.1/B4/C/D 的分歧记录不应被误读为完整兼容证明。
- `tools/oracle/`：上游 Lua 行为对照。涉及第三方代码/输出时必须复核许可。
- `stele-bench`：必须注明 `--scheme-dir`、`--schema`、是否真实词库、缓存冷/热、记忆和预测开关。内嵌演示词库的纳秒数字只能表示管线下限。

## 7. 不应回归的现有优点

整改时必须保留或用更强证据替代以下能力：

1. `unsafe_code = "deny"`；
2. 核心 `stele-core` / `stele-engine` 的小依赖面；若引入依赖，必须更新许可门禁和威胁模型，不可静默绕过；
3. 方案数据与内核分离；
4. 分数和排序的确定性；
5. 候选来源、拼写属性、输入/预测通道的显式类型；
6. 默认关闭的用户记忆和可观察的记忆导出；
7. 坏记忆文件不自动覆盖；
8. 配置错误有可读诊断；
9. 对照 Rime 的可重跑工装；
10. 回归测试优先于“这次手工看起来能打”。

其中某些实现注释有不准确表述，也应修正。例如 Rust `&str` 的 `==` 比较字符串内容，不要求指针相同；因此不要把 `Box::leak` 的标签处理解释为 `Vec::contains` 必须依赖同一内存地址。若仍选择 intern/常驻字符串，应基于其运行时分配和生命周期取舍，而非错误的相等性前提。

## 8. 最终产品方向建议

如果近期目标是让用户获得一个省资源、隐私更可控的手机中文输入体验，应并行评估成熟 Rime 前端 + 精简本地方案；这比等待新内核补齐全部基本能力风险更低。实际资源占用仍需在目标手机测量。

如果长期目标是独立 Rust 输入法，Stele 值得继续，但路线应是：

```text
可靠保存/缓存 + 有界搜索
    → 音节图/词图/会话编辑
    → 词级读音和质量评测
    → 明确的配置子集与资源图
    → 隐私/许可/前端真机验收
    → 再考虑预测、向量、更多插件
```

最重要的产品顺序是：**先保证“字打得出来、打得对、不卡、不丢”，再追求 AI、插件数量和宣传上的全面胜过 Rime。**
