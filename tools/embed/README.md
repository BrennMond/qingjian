# tools/embed — 本地向量偏好记忆的对比集

与 `tools/predict/` 同一条约定：这里的每一样东西都是**验收线**，
不是运行期资产；它不参与构建，也不被内核 crate 引用。

| 文件 | 是什么 |
| --- | --- |
| `context-cases.tsv` | `history`（用户打过的句子）+ `case`（留出用例：上文 → 待输入编码 → 期望词）。**它就是"向量有没有用"这句话的可证伪形式** |

## 怎么跑

```bash
cargo test -p stele-embed --test context_cases -- --nocapture
```

测试会读这张表、按它生成一份临时方案，然后做一次 **A/B 对照**：

- **A 基线**：词库权重 + P4a 精确记忆（= 今天的产品）；
- **C +向量**：再挂上 `stele_embed::EmbedRanker`。

并同时断言两件事：**改善**（基线错的被修好）与**无净损失**（基线对的仍对）。

## 格式

每行 TAB 分隔，第一列是 `history` 或 `case`，后面是**交替的 (编码, 词) 对**：

```
history	jin tian	今天	tian qi	天气
case	jin tian	今天	tian qi	天气
```

- `history` 行会被依次上屏——它同时喂给 P4a（按编码）与预测表（按上下文），
  而**向量就是从预测表学出来的**。
- `case` 行的最后一对是「待输入的编码 + 期望词」，前面的对是上文。
- 同一个编码下的多个词（`tian qi` → `天气` / `田七`）是**必要的**：
  它们让"该选哪个"只能由上下文决定。

## 加一行的纪律（**这条比格式更重要**）

- **期望词的 P4a 次数要压得比对手低**，否则基线本来就对，用例区分不了向量。
- **不许用真实按键日志**（与"不记录按键日志"的隐私承诺冲突）。
- **不许用"向量模型生成、再用向量拟合"的合成历史**——那证明的是生成器，不是收益。

## 现状（诚实交代）

现在只有 **3 条用例**，而且是实施者自己写的。它证明的是**机制成立**，
不是"在真实打字上一定更好"。要回答"值不值得默认开"，需要一份
**所有者手写**的、覆盖真实打字习惯的更大的用例集。
详见 `docs/embed-design.md` §3 与 §6。
