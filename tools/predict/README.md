# tools/predict — 下一词预测的对比集

这里的每一样东西都是**验收线**，不是运行期资产。它不参与构建，
也不被内核 crate 引用（内核不许有数据文件——门禁抓到过一次）。

| 文件 | 是什么 |
| --- | --- |
| `collocations.tsv` | `(上一/上两个词 → 期望的下一个词)` 的存档表。**它就是"常见搭配排序改善"这句话的可证伪形式** |

## 怎么跑

```bash
cargo test -p qingjian-memory --test predict_next
```

测试会读这张表、按它生成一份**临时方案**（拼音音节表 + 词库都来自表里的编码），
然后对每一行：

1. **基线**：一份全新的记忆里把链的前面那些词上屏 → 断言期望词**还没有**被预测出来；
2. **学**：把整条链上屏若干遍（走完整的"按键 → 上屏 → 事件 → 记忆"那条链）；
3. **验**：换一个全新的会话、同一份记忆，再把前缀词上屏 →
   **断言期望词是预测通道的第 1 位**。

基线那一步不是装饰：没有它，"期望词在第 1 位"可能只是"它恰好从别处冒出来"。

## 为什么不内嵌一份通用搭配表

见 HANDOFF §7.7.2 ④ 的所有者决定：**只留接口 + 本地自建**。
`PredictionOrigin::General` 这条通路在类型上留着，但今天唯一的预测来源
只能是用户自己的打字历史（`PredictionOrigin::Personal`）——
这与 P3.5 的教训一致：许可不明的数据比 GPL 更难处理。

## 加一行

在 `collocations.tsv` 末尾加一行 `编码 <TAB> 词` 的交替对即可。
两对 = bigram 用例，三对（或更长）= trigram 用例。
**每一行是独立的一份记忆**，所以不必担心行与行互相污染。
